### 실행과 글자 — 승인 시스템이 자기 자신을 막았다

포먼 세션은 enforce라 이 작업 중의 명령도 판정을 받았다. 세 번 연속 승인 창이 떴다:
1 · 2. 규칙 파일을 Bash heredoc(`cat > … <<'EOF'`)으로 쓰는데 본문의 `mkfs` · `rm -r` · `drop table` 글자가 걸렸다
3. 커밋 메시지(`git commit -F - <<'EOF'`) 본문의 글자가 걸렸다

고친 것(README 3.3 "실행과 글자는 다르다"):
- 텍스트로 저장만 되는 곳(`cat > 파일`, `tee 파일`, `git commit/tag/notes/merge -F -`, `gh … --body-file -`)에 들어가는 heredoc 본문은 검사하지 않는다
- 실행기(bash · sh · python …)로 들어가는 heredoc은 검사한다. `.sh`로 쓰는 것도 검사(곧 실행될 것으로 본다)
- **스크립트를 실행할 때**(`bash x.sh`, `source x`, `./x.sh`) 파일 내용을 읽어 검사한다 — heredoc이든 Write 도구든 숨긴 위험 명령은 실행 순간 잡힌다. `bash -c '…'` · `vagrant ssh … -c '…'`는 안쪽 명령으로
- 따옴표 없는 heredoc(`<<EOF`) 본문의 `$( )` · 백틱은 셸이 실행하므로 받는 쪽이 커밋이어도 검사한다
- 규칙 파일(`config/approval.toml`, `notify.toml`)은 보호 파일 — 쓰기 자체가 ask

### 이 과정에서 사용자가 짚은 것

- **규칙을 커밋만 하고 브리지를 재시작하지 않았다** — 옛 규칙이 계속 돌았다. 재시작 뒤 `kubectl apply` → allow 확인. 규칙 파일을 바꾸면 다시 띄운다(메모리에 남김)
- **파일을 Bash의 python heredoc으로 고치고 있었다** — 이유는 없었다(여러 곳을 한 번에 바꾸는 습관). 그 본문이 실행기로 들어가니 정책이 검사하는 것이 맞다. 이후 파일 수정은 Edit/Write 도구로만(메모리에 남김)
- `809469c`는 테스트 2개가 실패한 채 커밋됐다 — 명령이 `pytest … | tail -1`의 성공만 보고 넘어갔다. 실패는 5단계 DB 테스트가 ask 예로 `kubectl apply`(이제 allow)를 쓴 것. `45f0a8f`에서 고침
- `45f0a8f`에 `git mv`로 미리 스테이징한 `index.html → debug.html` 이름 바꾸기가 딸려 들어갔다 — 그 커밋에서는 `/`가 없는 파일을 가리켰다(다음 커밋에서 맞춤)
- hook 스크립트 시험에 쓴 가짜 세션 `x`가 세션으로 남아 있었다 — 판정 이벤트 3건과 함께 지움

### 사용 뒤 고친 것 — 모든 세션이 "포먼"으로 보였다

사용자가 대시보드를 열자 런슈즈 · 펫퍼민트 · 포먼의 세션이 전부 "포먼"으로 나왔다(미분류만 '미분류'). 2단계에서 기존 세션을 그 프로젝트의 포먼 캐릭터에 `role = coder`로 입양했고, 카드가 캐릭터 이름을 제목으로 썼기 때문이다.

- **판단**: 세션마다 캐릭터를 만들지 않는다 — 캐릭터는 영속이고 포먼만 채용한다(README 2.4), 재배치는 캐릭터를 제대로 만들 때(2단계 사용자 결정). 화면에서 세션을 알아볼 이름을 따로 쓴다
- **세션 이름**: CC가 대화를 보고 붙이는 제목(트랜스크립트 `ai-title` 줄의 `aiTitle` — 대화가 흘러가며 바뀐다). `0011` `character_session.title`, 조립기가 바뀔 때만 갱신(같은 제목이 런슈즈 한 세션에 4,457번 반복된다), 이미 있던 31개는 브리지 시작 때 트랜스크립트 끝 4MB에서 채움. 제목이 없으면 살아 있는 프로세스의 CC 세션 이름(`sessions/<pid>.json` `name`, 예: `petmint-rag-chatbot-33`), 그것도 없으면 짧은 id
- **화면**: 카드 제목 = 세션 제목, 아래 줄 = 캐릭터 · 역할 · 짧은 id · tmux pane. 예: 펫퍼민트 정지 세 개가 "docs 와 코드 불일치 점검" · "FAQ 전량 재구축 파이프라인" · "petmint 강아지 FAQ 질문 재작성"으로 갈린다
- **⚠ 임시 조치다.** 모든 세션이 포먼 캐릭터 하나에 묶여 있는 것은 11단계에서 포먼이 캐릭터를 제대로 만들기 전까지의 임시 상태다. **11단계에서 세션별로 올바른 캐릭터에 재배치해야 한다** — README 2.4 경고 · 로드맵 11 할 일에 남김

### 사용 뒤 고친 것 — 펫퍼민트 카드에 포먼에게 보낸 프롬프트가 보였다

사용자 보고(20:2x): 펫퍼민트 `cddadc68` 카드가 ACTIVE이고, 포먼에게 보낸 "대시보드 떴어. 버그 하나 있어…"가 거기 보인다. 포먼 `161b8e7a`는 IDLE.

- **매핑은 맞았다.** 최근 이벤트는 모두 자기 세션 행으로 들어갔다. 두 트랜스크립트를 직접 비교하니 **같은 462자 메시지가 두 터미널에 따로 붙여넣어졌다** — 펫퍼민트 10:35:16(붙여넣기 id `76fc`), 포먼 10:35:33(`163c`). 붙여넣기 id가 달라 CC 쪽에서 두 번의 입력이다. 화면 지연이나 귀속 오류가 아니라, 펫퍼민트 창에도 실제로 들어간 입력이었다
- **ACTIVE 판정이 틀렸다.** 규칙이 "CC status가 busy **이거나** 열린 턴이 있으면 ACTIVE"였다. 그 펫퍼민트 턴은 API 요청 뒤 응답도 끝 신호도 없이 10시간째 열려 있었고(CC status는 idle) — 그래서 ACTIVE로 보이고, 오래전 마지막 도구(Bash python3)가 "지금 하는 일"로 보였다
- 고침: 프로세스가 살아 있으면 **CC가 직접 적는 status가 기준**(busy → ACTIVE, 그 밖 → IDLE). 열린 턴은 status를 모를 때만 본다. 열린 턴이 있는데 CC가 일하지 않으면 `stuck_turn` — 카드에 "⚠ 끝 신호 없는 턴(n시간째)"로 숨기지 않고 보인다
- 그 펫퍼민트 턴이 왜 멈췄는지 — 사용자가 잘못 붙여넣고 **곧바로 Esc**로 중단한 것. Esc는 Stop hook을 부르지 않고(4단계 실측), **첫 응답 전에 누르면 `[Request interrupted by user]` 줄도 남지 않는다**. 트랜스크립트엔 프롬프트와 API 요청 줄뿐

### 끝 신호 없이 버려진 턴 — `abandoned`

- 실측: 지금 그런 열린 턴은 1개(펫퍼민트, 599분 · 활동 0 · CC idle). 응답 없이 닫힌 `merged` 66개의 다음 입력까지 간격은 최대 56분, 1시간 넘는 것 0 — 진짜로 합쳐진 것만 있었다
- 기준 1시간(`turn_abandon_s`): ① 살아 있는 프로세스 · CC가 일하지 않음 · 열린 턴이 1시간 넘게 조용 → 정리 작업이 `abandoned`(마지막 활동 시각으로), ② 응답 없던 앞 턴 뒤 다음 입력이 1시간 넘어 오면 `merged` 대신 `abandoned`. 1시간이면 실측 merged(최대 56분)를 잘못 닫지 않는다
- 재시작 때 정리 작업이 펫퍼민트 턴(5445)을 `abandoned`로 닫았다(10:35:16). 과거 merged 중 1시간 넘은 것이 없어 기존 행은 고치지 않았다
- README 3.2에 "Esc 중단은 흔적을 남긴다 — FOREMAN이 다루는 법"(언제 눌렀나에 따라 남는 것, 화면 · 정리 · 다음 입력 규칙)

## 설계와 달랐던 점

- **ACTIVE = 열린 턴** → CC가 sessions json에 쓰는 status(busy)가 더 빠르다. 둘 중 하나면 ACTIVE
- **화면이 모든 이벤트를 그린다** → 데이터는 바로 고치되 그리기는 주기로, 영역별로
- **토큰 = 세션 합계** → 본인 / 서브에이전트를 나누고, 서브에이전트 출력은 "추정"(3.11 — 응답 시작 시점 값)
