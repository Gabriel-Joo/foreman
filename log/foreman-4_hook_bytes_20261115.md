# 훅 스크립트가 입력을 바꿔 400이 난 원인과 고치기 (11-15, foreman-4)

관리자 410의 긴급 일감. 489(`cd14ed6`)를 합친 뒤 `/hooks/pre`가 400 「JSON이 아님」을 셋 중 하나꼴로 받아 PreToolUse 판정이 그 호출에서 꺼졌다. 관리자가 `1d303b9`로 스크립트만 되돌린 상태에서 시작했다.

## 원인 (재현으로 확정)

**stdin이 소켓이면 `body="$(</dev/stdin)"`이 열기에 실패해 0바이트 본문이 나갔다.** 셸 변수를 거치며 바이트가 바뀐 것이 아니라, 아예 읽지 못했다.

- bash의 `$(</dev/stdin)`은 fd 0을 그대로 읽지 않고 `/dev/stdin`(= `/proc/self/fd/0`)을 **새로 연다**. fd 0이 소켓이면 리눅스는 이 열기를 거부한다(ENXIO, 「No such device or address」). 변수는 비고, `printf '%s' ""`가 curl에 빈 본문을 넘기고, 브리지 `json.loads(b"")`가 400을 낸다. 옛 스크립트는 curl이 fd 0을 그대로 읽으므로(`--data-binary @-`) 소켓이어도 된다
- Node는 자식 프로세스 stdin에 소켓쌍을 쓴다. 이 꼴(`socketpair`)로 재현하면 489 판은 입력 꼴과 상관없이 모두 0바이트를 보냈다
- 맞는 증거: `.run/hook_miss.log`의 400 57줄이 **모두 `session=-`**(본문이 비어 세션을 못 읽음). 20:10~20:17 사이 1~13줄/분
- **「셋 중 하나꼴」인 까닭은 확인하지 못했다.** 그 시각에 CC가 두 판으로 돌고 있었다(지운 옛 실행 파일로 도는 프로세스 6개, 새 판 1개 — `/proc/<pid>/exe`). 판이나 훅 실행 길에 따라 stdin이 파이프 또는 소켓으로 갈리는 것으로 짐작한다. 실제 훅을 건드리지 않고는 가를 수 없어 짐작으로 둔다(고친 판은 어느 쪽이든 같다)

### 꼴별 재현 (가짜 서버가 받은 바이트를 원래와 맞댐)

| 입력 꼴 | 489, stdin 파이프 | 489, stdin 소켓 | 옛 판, 고친 판(두 꼴 모두) |
|---|---|---|---|
| 평범한 JSON, 역슬래시, 따옴표, 탭, 한글, 이모지, 잘못된 UTF-8, 셸 글자(`$`, 백틱 등), 128KB 넘는 입력 | 같음 | **0바이트** | 같음 |
| 끝 줄바꿈 하나 또는 여럿 | **끝 줄바꿈이 사라짐** | **0바이트** | 같음 |
| CR 섞인 줄바꿈(끝에 줄바꿈) | **끝 줄바꿈이 사라짐** | **0바이트** | 같음 |
| NUL 바이트 | **NUL이 빠짐**(한 바이트 짧음) | **0바이트** | 같음 |

파이프 쪽 차이(끝 줄바꿈, NUL)는 JSON 해석에는 영향이 없어 400의 원인은 아니다. 그래도 「한 바이트도 바꾸지 않는다」에 어긋나므로 함께 막았다.

### 지난 기록으로 넓게 (4번)

트랜스크립트의 실제 tool_use 입력 1500개(최근 트랜스크립트 400개에서, 400을 받은 20:10~20:17 시간대 60개 포함)로 CC의 PreToolUse 꼴(한 줄 JSON)을 메모리에서 만들어 흘렸다. 길이 중앙값 771B, 최대 약 36KB, 비ASCII 포함 1007개, 끝 줄바꿈 0개. 입력은 파일로 남기지 않았고 내용은 찍지 않았다.

| 판 | stdin 파이프 | stdin 소켓 |
|---|---|---|
| 옛 판(`1d303b9`) | 같음 1500, 다름 0 | 같음 1500, 다름 0 |
| 489 판(`cd14ed6`) | 같음 1500, 다름 0 | 같음 0, **다름 1500** |
| 고친 판 | 같음 1500, 다름 0 | 같음 1500, 다름 0 |

실제 입력에서는 내용 꼴이 아니라 stdin 종류 하나가 갈랐다.

## 고친 것

| 파일 | 무엇 |
|---|---|
| `scripts/foreman-decide.sh` | 489의 12갈래 기록을 되살리되 입력을 변수에 담지 않는다. `tee -p`가 fd 0을 그대로 읽어 curl에 흘리고, 곁가지(프로세스 치환)가 앞 4KB만 받아 `"session_id"`, `"tool_name"` 키의 값만 뽑아 이름 없는 파이프(`exec {IDS}<> <(:)`)로 넘긴다. 통과할 때 `miss()`가 그 파이프에서 읽는다. 임시 파일을 만들지 않고, 명령 글은 어디에도 쓰지 않는다. 파이프를 못 만들면 옛 판처럼 curl이 stdin을 바로 읽고 기록의 세션, 도구가 `-`일 뿐이다 |

| `docs/11_worktree.md` 7절 「한계」 | 훅 스크립트가 입력 바이트를 그대로 넘긴다는 한 문장 |

- 새 시험을 489 판에 대 보면(스크래치 사본) 18개가 실패한다: 소켓 꼴 전부(빈 입력 빼고), 파이프의 끝 줄바꿈 · 줄바꿈 여럿 · CR 섞인 줄바꿈 · NUL. 고친 판은 모두 통과
- 세션 id와 도구 이름을 앞 4KB에서만 찾는 것은 489와 다르다(489는 입력 전체). CC 입력은 두 키가 `tool_input`보다 앞이라 4KB 안에 든다(같은 방법으로 만든 실제 입력 5000개에서 `tool_name` 값이 끝나는 자리가 가장 멀어도 490바이트, 4KB 넘는 것 0개. 앞쪽 `transcript_path`, `cwd` 길이가 좌우한다). 처음 나온 값만 쓰고 모양이 안 맞으면 `-`인 것은 그대로다
- 이 서버의 `tee`는 GNU가 아니라 uutils 판이다. `-p`에서 곁가지가 4KB 뒤 닫혀도 curl 쪽에 끝까지 흘리는 것을 300KB 시험과 200KB 비교로 확인했다. coreutils가 바뀌면 이 시험이 먼저 잡는다
