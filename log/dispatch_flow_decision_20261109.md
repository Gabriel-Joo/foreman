# 세션 띄우기 흐름 — 교장을 키운다, 관리자는 상주로 두지 않는다 (2026-11-09 저녁, 원본 폴더)

## 정한 것(사용자 11-09)

- 흐름을 "교장 → 관리자 → worktree"로 고정하지 않고 **교장을 키운다**. 관리자(FOREMAN main 세션)는 **상주로 두지 않고 필요할 때만** 쓴다
- 할 일 넷(README 「나중에 할 일」): ① 교장이 한 번에 여러 세션 계획 ② 교장에게 읽기 전용 확인 도구 ③ 교장의 발견을 경고 · 질문 칸에 ④ 모든 띄우기가 계획 기록(dispatch)을 남김 — ①이 먼저

## 이어서 정한 것 — 들어오는 일을 종류대로(사용자 11-09)

- 오늘 메인에 온 지시: 할 일에 넣어라 ≈ 10 · 질문 · 분석 ≈ 5 · 운영 ≈ 4 · 코드 1 · 세션 띄우기 1 → 맥락이 쌓여 두 번 인계한 주된 까닭은 띄우기가 아니라 할 일 · 질문
- **먼저: 할 일 받는 칸** — 받은 글을 브리지가 세션 없이 그대로 적고, 정리 · 우선순위는 서기가 몰아서
- 그 뒤: 띄우기 → 교장에게 바로 말 걸기(간단한 기준 안), 질문 · 분석 → 그때 띄우는 읽기 전용 점검 세션, 운영 → 브리지
- 안 가는 것: "지시는 관리자에게, 띄우기만 기록" — 맥락이 쌓이는 문제를 그대로 남긴다

## 첫 적용 — 코더 상주 일을 교장 경로로(19:4x KST)

- 사용자: 코더도 서기처럼(상주 · 임시 일꾼 · [쉬게 하기]/[이어서] · 맡길 일 N · 받는 칸 '누구에게' · 정리 제안 말풍선), **worktree 코더에게 · 교장 경로로**, 맡길 일 = '코더에게' 받은 할 일 + 기계 신호(쉬게 한 일 · 빌드 실패 · 걸린 승인)
- 메인이 지시문을 쓰고 짧은 요청으로 교장에게 계획을 받음(**dispatch #152**, 경고 · 질문 없음, 확신도 0.75) → 첫 글을 지시문으로 바꿔(`edited`로 남음 — 계획 카드에서 사람이 칸을 고치는 것과 같은 경로) 시작 → **세션 233**, worktree `foreman-2`(`cc/foreman-2`)
- "걸린 승인"은 지시문에 빠져 세션 간 메시지로 보탰다
- 합치기 · 시험 · push · 브리지 다시 띄우기 · 화면 점검은 메인
- **스키마 잠금에 막힘**: 233이 0028(`todo_inbox` 받는 사람)을 못 씀 — 잠금은 메인(168ece53)이 17:16 0027 적용 때 잡은 것, 원본 폴더 세션은 세션이 끝날 때까지 쥔다(`bridge/schemalock.py` `_held`). 화면에 [풀기]가 없고(설계는 "사람이 푼다", API만 있음) 원본 폴더 세션의 잠금은 화면에 보이지도 않는다. 233이 막힌 것도 233이 메시지를 보내서야 알았다(조용한 고장)
  - 사용자 지시로 **이번 한 번 메인이 API로 풂**(`DELETE /api/schema-lock/foreman` → released)
  - 고칠 것(사용자: 233에 보태기) — 지시문 7번: ① 잠금 표시(누가 · 언제부터 · 무엇) + [풀기] ② 잠금에 막히면 화면 띠 + 텔레그램 ③ 원본 폴더 세션은 적용 · 커밋 끝이면 저절로 풀기
  - **바로잡음(20:1x)**: 메인이 쥔 잠금은 **0027 적용(19:33) 때가 아니라 17:16 읽기 전용 DB 조회 때** 잡혔다 — 명령 패턴 `bridge\.db\.migrate`(`config/worktree.toml`)가 `from bridge.db.migrate import connect`(DB에 붙으려고 가져오기만)에도 맞는다. 233의 "0027 때"를 확인 없이 옮겼다. 20:1x에는 반대로 메인의 읽기 조회가 233의 잠금에 거부됨 → 7번 ④로 보탬: 마이그레이션을 **돌리는** 명령만 맞게(`-m bridge.db.migrate` · `bridge/db/migrate.py`), 가져오기는 제외

## 메인 세션 역할 코더 → 관리자(사용자 20:5x)

- 역할 값은 새로 `manager`(화면 "관리자") — `foreman`은 감독실 교장 · 팀장 캐릭터(세션 없는 계획 창구)라 섞지 않는다
- 세션 역할을 바꾸는 API가 없고(띄울 때만 정해짐) 화면 이름표에 manager · scribe가 없어서, **화면 · API를 코더 worktree에 먼저**: 교장 경로 dispatch #158 → 세션 242(`foreman-3`, opus). README 「세션 제목 맨 앞에 역할」 일도 같이(사용자: "그것과 같이 맞춰라"). 합친 뒤 메인이 새 API(`PUT /api/sessions/{sid}/role`)로 자기 세션 230을 manager로
- 관리자가 코드를 고쳐도 되는 기준은 메인이 CLAUDE.md 「작업 규칙」에 바로 적음(설정 · 기록 몫): 합친 뒤 깨짐을 막는 되돌리기 · 몇 줄, 시킨 설정 값 · 기록 · 나중에 할 일 줄, 동작이 안 바뀌는 한두 줄 — 그 밖은 작아도 worktree(작으면 sonnet)
- 같은 때 떠 있는 worktree: 237(서기 — 나중에 할 일 정리, `foreman-2`, 받은 할 일 #2~#11 → README) · 242(README 줄 ✅) — **둘 다 README를 고치므로 237을 먼저 합친다**. 238(Explore, `foreman-3`)은 20:49 사용자가 화면에서 합침(`9544e67`) — 그 이름을 242가 다시 받음

- **교장도 알림 셋이 이미 있다는 것을 알았다** — 132 이유 칸(관리자 말보다 앞): "알림 쪽 … 세 가지는 인계 요약(summary 20)에 이미 넣었다고 적혀 있다. 알림 세션을 띄우기 전에 남은 것을 확인해야 한다". `warnings` · `questions`는 비어 있었다 → 카드에서 눈에 띄지 않았다
- 차이: 교장은 문서로 읽었고, 관리자는 코드 · 기록 · 브리지 기동 시각으로 실제로 도는지 확인했다
- 관리자 검토가 값을 낸 다른 예(오늘): 합친 뒤 지시문의 모순("화면 worktree 몫은 쓰지 말라")을 고침 · 띄우기 전 worktree 바탕 커밋 확인 · 대화에서만 정한 결정(2 · 3단계 나중) — 대부분 **교장에게 정보가 닿지 않아서**였다

## 관리자를 상주로 두지 않는 까닭

- 하는 일을 나눠 보면 세션이 꼭 들고 있어야만 하는 것이 없다 — 띄우기 · 지시문은 교장 + 버튼, 합친 뒤 시험 · push · 다시 띄우기 · 확인 목록은 브리지가 할 수 있고, 조사 · 설계 답 · 코드 · 기록은 그때 띄우는 점검 · 코더 · 서기 세션으로
- 상주면 맥락이 쌓여 압축된다 — 교장을 "부를 때만"으로 둔 까닭과 같다
