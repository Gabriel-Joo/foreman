## 2. 왜 규칙이 13줄 쌓였나 — dispatch 기록으로 본 것

운영 DB `foreman_note` kind decision 16줄(살아 있는 15 + 11-10 내린 1171)과 그 줄의 `dispatch.plan` · `edited`를 읽었다(scratchpad 스크립트, 읽기만).

- **16줄 모두 교장이 계획마다 1줄씩 제안했고, 사람이 [시작] 때 16개 모두 켠 채 시작했다**(시작한 계획의 decision add — 켬 16 · 끔 0). 계획 107건 중 노트 제안이 있는 것 57건
- **지시문이 쌓으라고 시켰다.** 9번이 「쌓는 것은 둘뿐: thread · decision(사람이 정한 판단 · 금지 — 사람의 말이나 log에 근거가 있는 것만)」이었다. 설계 문서 3절의 「쌓지 않는 것: 구조 · 자주 쓰는 명령」도 지시문의 「쌓지 마라: 저장소 구조 · 자주 쓰는 명령 · 파일 경로 목록」도 **규칙 · 설계 결정은 막지 않았고**, 오히려 「금지」는 decision의 정의 안에 들어 있었다. 교장은 지시문을 어긴 것이 아니라 지킨 것이다
- **빈 노트가 부추겼다.** 노트가 비면 묶음에 「(아직 없음 — … 사람이 정한 판단이 보이면 decision을 제안하라)」가 들어갔다. 사람이 정한 판단은 거의 모든 요청에 「보인다」
- **요청 글이 늘 근거를 줬다.** 관리자가 넘기는 요청이 「사용자 지시(11-10)」 「사용자 결정」으로 시작한다 — 예: dispatch 189 「글씨 배율 범위를 다시 잡아라 … 90%가 보기 좋다」 → 1097, 209 「[코더 — 서기 재료 잘림 …] 사용자 지시(11-10)」 → 1201, 232 「관리자 세션에만 … push 허용 … (사용자 11-10)」 → 1333, 240 「[계획에서 「확인을 기다려라」 빼기 …]」 → 1349, 407 「check_watch TypeError 고치기」 → 2240(「나중에 할 일이 아니라 지금 고칠 일이다」). 「사람의 말에 근거가 있는 것만」이라는 거르개가 늘 통과됐다. 일감의 지킬 것이 그대로 decision이 되어, 일이 끝나도(커밋 · 문서에 들어가도) 줄은 남았다
- **사람이 볼 기회가 적었다.** 계획 카드의 노트 제안은 11-09 사용자 지시로 접혀 「노트 고치기 제안 N개」만 보이고 기본이 켬이다. 펼쳐 끄지 않으면 들어간다
- **decision 줄은 내려가는 길이 없었다.** 11-13 자동 내리기 · 낡음은 thread만 보고, decision은 상한(2000토큰)에서 접힐 뿐이었다. 그래서 끝난 일 8줄(2240 · 1232 · 1394 · 1248 · 2242 · 1096 · 409 · 114)도 판단으로 남았다
- **334가 오늘 decision을 하나 더 시켰다**(관리자 띄우기 → 「X 관리자가 있다」, 2845). 이번에 되돌렸다

이번에 막은 곳: 지시문(쌓지 않는 것에 규칙 · 설계 결정 · 판단을 이름으로, 「사용자 지시」는 첫 글로, 낱말 decision 자체를 뺌) · 빈 칸 부추김 문구 · 코드(제안이 와도 빼고 카드 경고 — 지시문을 어기면 사람이 본다).

## 3. 「확인 뒤 커밋」 — 글에서 떼고 낡음 문턱에만

- **뗐다**: 줄마다 붙던 「⚠ 확인 뒤 커밋 N개」(와 셀 수 없을 때 「확인 뒤 HEAD가 바뀜」). 이 수는 **저장소 전체 커밋**이라 그 줄의 일과 상관이 없다. FOREMAN은 하루 커밋 60 ~ 110개(`log/note_auto_retire_20261113.md` 5절)라 진행 중인 일 거의 모든 줄에 하루 안에 붙어 늘 켜진 표시였다 — 교장이 「⚠ 붙은 줄은 그대로 믿지 말라」를 받으면 모든 줄을 의심하게 되고, 그만큼 정말 볼 표시(「확인 뒤 세션 N에 활동 있음」 · 「출처 파일이 없음」)가 묻혔다. 판단 칸이 있을 때는 decision에도 붙었다(200 ~ 350개)
- **남겼다**: 커밋 수 계산과 낡음 문턱 `stale_commits`(11-13 사용자가 `config/wake.toml`에 150으로 적은 값). 런슈즈 2238처럼 날수보다 저장소가 빨리 움직인 줄을 먼저 「낡음」으로 거는 데 쓰인다. 낡음 까닭(「확인 필요 — 확인 뒤 커밋 219개」)에는 그대로 둔다 — 줄이 왜 낡음으로 갔는지의 설명이고, 문턱을 넘은 줄에만 붙는다
- 진행 중인 일에 남는 ⚠는 세션 활동 · 출처 파일 둘이다

## 4. 판단 줄 15개 내리는 법(제안 — 관리자가 사용자 지시대로)

코드만으로 이미 묶음 · 패널에서 빠진다 — 운영 DB 그대로 이 worktree 코드로 `render` 해 보니 FOREMAN 113 · 펫퍼민트 509 · 런슈즈 2238만 들어가고 decision 15줄은 0줄(읽기만, `PYTHONPATH`로 이 폴더 코드). 그래도 DB에 살아 있는 채로 두면 나중에 칸을 되살릴 때 섞이니 내린다.

## 5. 되돌리는 법

- 코드 · docs · 시험: 이 커밋을 `git revert`. 스키마 변경 없음. 브리지는 합친 뒤 원본 세션이 다시 띄워야 지시문 · 묶음이 바뀐다
- 4절로 내린 줄 되살리기: `UPDATE foreman_note SET retired_at = NULL WHERE id IN (…) AND kind = 'decision';` — 단 이 코드가 도는 동안은 되살려도 묶음에 안 들어간다(revert와 함께)

## 6. 설계와 달랐던 점

- 1349는 이미 지시문에 있었다(위 4절). 「옮기기」가 아니라 문구 맞추기 + 문자열 시험
- 1201은 docs에 없었다(위 4절)
