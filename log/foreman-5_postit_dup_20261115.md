# 포스트잇 p:51 같은 근거 여러 장 조용히 잃음 고침 (11-15, foreman-5)

## 고장
관리자가 `POST /api/postit`로 같은 세션에서 21장을 올리면 한 장만 생기고 나머지 20번도 성공처럼 같은 id를 받았다. 근거(`source_ref`)가 그 세션의 마지막 사람 턴(`t:<턴>`)이라 한 턴 안에서 올린 장은 모두 같은 근거였고, `add`가 근거만 같으면 새로 만들지 않았다.

## 「같은 근거면 한 장」이 있던 까닭
브리지 그물(`sweep`)이 같은 대화 턴을 여러 번 주워도 한 장만 만들게 하려는 것, 그물이 먼저 올린 확인 전 줄에 관리자가 같은 턴으로 올리면 두 줄이 아니라 한 줄이 확인된 줄이 되게 하려는 것(`log/foreman-5_postit_20261115.md`). 이 둘은 지킨다.

## 바꾼 것
- `bridge/postit.py` `add`: 그물(`chat`)과 옮기기(`promote`)는 근거 하나에 한 장(`ONE_PER_REF`). 관리자(`said`)와 사람(`note`)은 같은 근거에 글이 다르면 모두 새 장. 같은 근거에 같은 글(앞뒤 공백 뺀 같음)만 겹침으로 보고 `{created: false, duplicate: true, reason}`을 돌려준다(API는 200). 그물 확인 전 줄은 같은 근거의 첫 글이 확인된 줄로 바꾸고(`upgraded: true`, 새로 만든 것으로 봄 201), 글이 다른 다음 것은 새 장
- 마이그레이션 없음(근거 칸은 유일 키가 아니라 그대로)
- 시험 `tests/test_stage2_db.py` 두 곳: 같은 근거에 글이 다른 세 장은 세 장, 같은 글 두 번은 한 장이고 응답이 겹침을 말함, 그물이 같은 턴을 다시 주우면 한 장, 세션으로 올린 여러 장 뒤에도 그물이 그 턴을 다시 올리지 않음. 옛 기대(같은 근거면 `created False`)는 새 기준으로 고침
- docs `docs/12_scribe.md` 11절 source_ref 줄과 API 줄

## 같은 id를 기대하던 곳(grep)
`pi.add`를 부르는 곳은 API `postit_add`와 `postit_save`(`id`만 씀, 근거 없음)와 그물 `sweep`뿐이다. 반환의 `created`는 API 상태 코드와 `sweep`의 새로 올린 수에만 쓴다. 화면 [저장]은 `/save`라 근거가 없어 영향 없음. 인계 「포스트잇에 올림」 · 확인 전 길은 코드에서 `add`를 따로 부르지 않는다.
