### 1-4. 한 번 돌 때 토큰

설계의 어림(`docs/12_scribe.md:155-174`, 회고 하루 15~25만 토큰 등)은 있지만 **실제로 일마다 재서 적어 둔 기록은 없다.** 서기 카드에 토큰이 보일 뿐 일감별 합계를 내는 코드도 없다. 그래서 DB에서 직접 셌다.

쿼리(서기 역할 FOREMAN 세션마다, 서브에이전트 포함, `<synthetic>` 뺌):

```sql
SELECT cs.id, (SELECT sa.detail FROM session_action sa WHERE sa.session_id = cs.id AND sa.action = 'scribe-task' LIMIT 1) AS task,
 COUNT(DISTINCT t.id) AS turns, COUNT(m.id) AS msgs, GROUP_CONCAT(DISTINCT m.model) AS models,
 SUM(m.token_input), SUM(m.token_output), SUM(m.token_cache_read), SUM(m.token_cache_creation), SUM(m.subagent_id IS NOT NULL)
FROM character_session cs JOIN `character` ch ON ch.id = cs.character_id JOIN project p ON p.id = ch.project_id
JOIN turn t ON t.session_id = cs.id JOIN message m ON m.turn_id = t.id
WHERE cs.role = 'scribe' AND p.name = 'foreman' AND m.model <> '<synthetic>' GROUP BY cs.id ORDER BY cs.id
```

버튼으로 띄운 것(`scribe-task` 있음). 입력 토큰은 모두 수십 개라 뺐다(거의 다 캐시 읽기다).

- 합쳐진 결과가 있으면 서기 창 문서 점검 줄 아래에 [바로 고치기]가 뜨고(`scribe.js:134-140`), 누르면 「문서 고치기」(`docfix`) 세션이 그 결과를 목록 삼아 README, docs/, CLAUDE.md만 고친다(`scribe_room.py:481-488`). 코드는 건드리지 않는다
- 같은 결과를 두 번 고치지 않게 합쳐진 docfix를 기억한다(`fixed_reports`, 139-148)

### 5-3. 화면 말 시험(`tests/test_screen_words.py`)과 무엇이 다른가

| | 문서 점검(서기) | 화면 말 시험 |
|---|---|---|
| 누가 | Opus 세션(LLM) | pytest(LLM 없음) |
| 언제 | 사람이 [시키기]를 누를 때 | pytest를 돌릴 때마다(관리자가 합친 뒤 손으로. CI 없음) |
| 무엇을 | README, docs, CLAUDE.md 전체의 경로, 파일, 함수, 설정 키, 명령, 숫자 | 목록(`tests/data/screen_words.toml`)에 적힌 것만: 안 A 바꾼 화면 이름의 옛 이름이 코드 문자열과 문서 인용에 남았나, 안 B 문서가 [버튼]으로 인용한 글이 지금 코드에 있나, 안 D 호버 설명이 약속한 조작이 약속 목록에 있나(`tests/screen_words.py:1-13`) |
| 결과 | `log/doccheck_*.md` 보고서 | 시험 실패(합치기 전에 막힘) |
| 고치기 | 따로 [바로 고치기] 세션 | 코더가 같은 브랜치에서. `docs/operations.md`, `docs/style_guide.md`에서 걸린 것만 `[[scribe]]` 「서기 몫」에 적어 통과시키고 서기가 나중에 맞춘다(`screen_words.py:10-11`, `27`, `416-428`) |

- 겹치는 곳: 「문서에 적힌 화면 글(버튼 이름, 화면 말)이 지금 코드와 맞나」는 둘 다 본다. 화면 말 시험은 그 가운데 목록에 오른 것과 [버튼] 인용만, 기계로, 매번 본다
- 겹치지 않는 곳: 경로, 함수, 설정 키, 숫자, 절차 설명이 맞나는 문서 점검만 본다(시험은 보지 않는다). 거꾸로 호버 약속(안 D)과 코드 문자열 속 옛 이름은 시험만 본다
- 「서기 몫」(`[[scribe]]`)은 서기실 할 일 숫자와 이어져 있지 않다. 남은 줄 수는 pytest 요약에만 찍힌다(`screen_words.py:462-463`)

## 6. 내가 보기에 지금 이상한 것

### 6-1. 쓸모가 없거나 겹치는 일

- **문서 점검의 숫자가 이름과 다른 것을 센다.** 「결과 없는 단계 N개」는 코드와 문서의 어긋남과 상관이 없다. 지금 0이라 줄에 숫자가 없어 「밀린 것 없음」처럼 보이지만, 실제로 11-10부터 버튼 밖에서 띄운 문서 맞추기 서기 세션(「docs 어긋남 맞추기」 등)만 15개다. 숫자가 일을 부르지 못한다
- **문서 점검과 그 뒤 문서 맞추기가 서기실 밖에서 따로 돈다.** 11-10부터 문서 맞추기는 계획 길(관리자, 디스패처, 역할 `scribe`, 대부분 Sonnet)로 15번 돌았고, 같은 기간 서기실 버튼의 문서 일(문서 점검, 문서 고치기)은 0번이다. 어느 세션을 관리자가, 어느 세션을 디스패처가 띄웠는지는 가르지 않았다. 서기실의 「열려 있는 일」, 겹침 막기(`TOUCHES`), 「나중에」 기준점 모두 이 세션들을 모른다. 같은 일을 두 길로 하는 셈이다
- **README 갱신과 관리자 일이 겹친다.** CLAUDE.md는 로드맵 표를 원본 세션(관리자)이 고친다고 하고, 서기 README 갱신도 같은 표를 고친다. 11-11 뒤 README 커밋 58개는 모두 서기 버튼 밖에서 났다. 밀림 숫자도 README를 아무나 한 줄만 고치면 0으로 돌아가 「README가 지금에 맞나」를 재지 못한다(지금 3)
- **나중에 할 일 정리의 89는 거의 일감 글이다.** 85턴 가운데 68턴이 붙여 넣은 일감 글이고 47턴이 관리자 세션이다. 정규식이 「나중에 할 일」이라는 표 이름 자체에도 걸린다. 받은 할 일(4개)은 진짜 할 일인데 이 숫자에 묻힌다
- **CLAUDE.md 정리는 지금 규칙과 부딪칠 수 있다.** 메모리 규칙 「관리자는 CLAUDE.md를 고치기 전에 사용자에게 묻는다(11-14)」가 있는데 서기 trim은 CLAUDE.md를 통째로 정리하는 일이다(합치기 때 사람이 보기는 한다). 80줄 상한은 11-05 설계의 「예시」 값이고(`scribe_room.py:22` 주석), 11-06 정리 뒤 CLAUDE.md를 바꾼 커밋이 18개다. 받은 할 일 #20(CLAUDE.md를 역할별로 나누기)이 같은 곳을 다른 방향으로 다룬다
- **회고는 쓰는 길만 있고 읽는 길이 없다.** 하나뿐인 회고는 Notion에서 내렸고, 코드에서 회고를 읽는 곳은 포트폴리오 00 재료 목록 한 줄뿐이다. 526이라는 숫자는 「얼마나 안 썼나」를 셀 뿐 「누가 기다리나」는 말하지 않는다
- **포트폴리오 [갱신]의 기준이 「서기가 쓴 때」가 아니다.** 메인 세션이 이름만 바꿔도 470이 0부터 다시 센다. 커밋 수도 그 글과 무관한 커밋을 모두 센다

### 6-2. 526까지 쌓이도록 둔 까닭(기록, 알림, 카드, 설정 근거)
