## 2. 집계 · 환산 · 창 · /usage 읽기 · /api/usage (11-08)

사용자 결정(11-08): 관찰은 `claude -p "/usage"`로(tmux 화면 읽기는 보조 — 오늘 세션 둘이 `/usage` 화면 때문에 막혔다). 주간 리셋은 **일요일 22:00**(앞서 말한 "토요일"은 사용자 착오, 11-08이 일요일).

- `bridge/usage.py`
  - 환산: `config/usage.toml` 가격표(모델 이름에 든 글자로), 표에 없는 모델(`<synthetic>`)은 0
  - `/usage` 글 풀이: `claude -p` 한 줄 모양과 tmux 여러 줄 모양(머리 · 막대 · Resets) 둘 다. 리셋 글 "Nov 8, 12:10pm (Asia/Seoul)" · "12:10pm"(지났으면 다음 날) · 연말 넘김. 줄 머리를 하나라도 못 찾으면 실패로 센다(글 모양이 바뀐 것을 조용히 넘기지 않게)
  - 창: 읽은 리셋이 앞이면 [리셋 − 창, 리셋). 지났으면 주간은 7일씩 넘기고, 5시간은 리셋 뒤 첫 메시지부터 다시 짓는다(`chain_windows`). 첫 메시지가 거꾸로 셈한 시작보다 몇 분 앞서도(10-23 사례) 읽은 창에 넣는다
  - 하한: 관찰마다 그 창의 환산액 `seen_usd` → 하한 = seen ÷ % × 100, 5% 아래는 뺀다, 높은 %에 무게, 범위 · 근거 수 · 10% 안이면 안정. 읽기 사이 추정 % = 측정 % + (지금 창 환산 − 읽을 때 환산) ÷ 하한. 최근 1시간 속도로 100% 시각, 리셋 전인지

## 5. 80 · 95% · "1시간 안에 5시간 한도" 알림 (11-08)

- `UsageMonitor.run`이 1분마다 돈다 — `/usage`는 `poll_s`(600초)마다만 읽고, 알림 판정은 매분(읽기 사이에도 추정 %가 오른다)
- 한도마다 추정(없으면 측정) % ≥ 80 → ⚠, ≥ 95 → 🛑(그러면 80%는 따로 안 보내고 `skipped`로 남긴다). 5시간 한도는 최근 1시간 속도로 100%가 1시간 안 · 리셋 전이면 ⏳. 글에 측정 % · 읽은 시각 · 리셋 · 이 속도면 언제 100%, /usage를 못 읽는 중이면 "FOREMAN이 본 사용량으로만 추정"
- 한 번만: 창(리셋 시각)마다 `notification.rule`(`usage:<한도>:<80|95|eta>:<리셋 MMDDHHMM>`) — `send_direct`에 선택 인자 `rule`을 더했다(기존 호출 그대로). 브리지를 다시 띄워도 DB를 보고 다시 안 보낸다
- **로그인 만료 알림이 재기동마다 또 나갔다**(709 · 710 · 711 — 메모리로만 막았다) → 같은 방식(`usage:login:<만료 시각>`, rule 없이 남은 옛 기록은 글로 찾는다)으로 고쳤다
- 실제: 재기동 13:12 → 주간 92%로 ⚠ 80% 알림 한 번(712, sent). 다시 재기동 → 새 알림 0(80% · 로그인 둘 다)
- 시험: 85% + 최근 1시간 $20 → 80% · ⏳, 96% → 🛑만, 다시 판정 0, 새 모니터(재기동)도 0, 낮은 문턱 `skipped`. 전체 470 통과

### 왜 하한인지 페이지에 (11-08, 사용자 요청)

- 사용자: 웹 Claude 세션도 길게 쓴다 — FOREMAN이 못 보는 사용이라 하한 $946은 실제보다 낮게 잡힌 것이고, 웹을 많이 쓸수록 실제 한도는 더 높다. "왜 하한인지가 안 보인다"
- 카드: "창 안 환산" → **FOREMAN이 본 것**, 새 줄 **못 보는 사용 — 웹 · 앱 · 다른 PC, 금액 모름**, "하한" → **한도 하한 $N 이상**
- 카드 아래 **왜 하한인가**: 측정 %는 모든 사용(이 PC의 CC + 웹 · 앱 + 다른 PC), FOREMAN은 이 PC의 CC만 → 실제 한도 = (본 것 + 못 보는 것) ÷ % ≥ 본 것 ÷ % = 하한, 지금 주간 값으로 예. 같은 이유로 추정 % · "언제 100%"는 웹을 함께 쓰면 실제로 더 빨리 찬다(다음 읽기에서 바로잡힌다)

## 6. 맥락 크기 알림 — 300k · 500k에서 인계 권유 (11-08, 사용자 승인)

- 까닭: 압축은 맥락이 꽉 찬 뒤에야 일어난다. 11-08 살아 있는 세션들이 압축 0번으로 300~470k에서 돌며 응답마다 그만큼 다시 읽었다(주간 사용의 57%가 캐시 읽기). 압축 횟수로만 판단하면 아무 알림도 없다
- 판정(`bridge/compactwatch.py`): 세션의 마지막 본 대화 응답(서브에이전트 아님)의 맥락 = 입력 + 캐시 읽기 + 캐시 쓰기. `notify.toml [compact] context_at = [300000, 500000]` — 첫 값 "넘어갈 때", 끝 값 "늦었음"
- 텔레그램: 턴이 닫힐 때(실시간 적재일 때만) 처음 넘은 문턱마다 한 번 — `notification` kind `context` · rule `ctx:<문턱>`(재기동해도 DB로 막음). 한 번에 둘을 넘으면 높은 것 하나, 높은 것을 보냈으면 낮은 것은 다시 안 보냄. 글에 "응답 하나에 맥락 읽기만 약 $N"(사용량 설정의 캐시 읽기 가격). 숨긴 세션 · 접두어 없는 프로젝트는 압축 알림처럼 뺀다
- 화면: 대시보드 세션에 `context`({tokens, model, at, level}), 패널 띠는 압축 띠 자리 — 압축 단계가 없으면 "🧠 맥락 473k — 넘어갈 때입니다 …" + [인계 요약 받기] · [나중에](다음 단계까지 숨김)
- 사용량 페이지 "왜 하한인가"에 "한도는 웹 · 앱 Claude, 다른 PC와 같이 쓴다 · 웹의 긴 대화도 응답마다 맥락을 다시 읽어 한도를 쓴다"를 직접 적었다(사용자 요청)
- 확인: 재기동 뒤 대시보드 200 473k · 170 350k · 211 334k → due, 212 122k → 없음. 세션 200을 고른 패널 사진에서 띠 확인, `screen.py` 세 테마 0건. 시험(문턱 · 한 번 · 글) 포함 전체 472 · JS 45 통과
