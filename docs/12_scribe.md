# 12 — 서기(문서화 캐릭터) 설계 (2026-11-05 초안, 사용자 확인 대기)

README 로드맵 12는 원래 "떠돌이 포트폴리오 작성 캐릭터"였다. 11-05 사용자 결정으로 **프로젝트마다 하나씩 두는 문서 담당**으로 바꿨다. 포트폴리오는 이 캐릭터가 하는 일 중 하나다.

## 1. 누구인가

| 항목 | 정한 것 |
|---|---|
| 역할 이름 | `scribe` — 화면 이름 **서기**. coder(코더) · inspector(점검) · cicd(CI/CD)와 같은 층위 |
| 캐릭터 | 프로젝트마다 "서기" 하나. 부모 = 그 프로젝트의 포먼, `spawned_by = foreman`(0017의 코더 · 점검과 같은 방식) |
| 색 | 잉크 갈색 `#b0713a` — 금색(포먼) · 파랑 · 초록 · 보라와 겹치지 않는다 |
| 상주 자리 | 테마의 `library` 구역 — 마법학교 "서고", 오피스 "아카이브". 현장은 `store`(자재창고) 대신 도면함을 둘 자리를 정한다. plain은 구역이 없어 하나 더한다 |
| 움직임 | 일이 없으면 서고에 앉아 있다(IDLE). 일하면 서고 책상에서 쓰고, 커밋할 때 커밋 데스크로 간다. 지금도 서고는 "파일 읽기" 일이 가는 곳이라 따로 만들 것이 적다 |

**맡는 일(일감 종류):**

| 일감 | 하는 것 | 내놓는 것 |
|---|---|---|
| `sync` 문서 맞추기 | 마지막 문서 갱신 뒤의 커밋 · log를 보고 README 로드맵 줄 · docs를 고친다 | 브랜치의 diff |
| `retro` 회고 | 기간(하루 · 단계)을 정해 한 일 · 판단 · 뒤집힌 결정 · 실수 · 숫자를 쓴다 | `log/retro_<날짜>_<주제>.md` |
| `portfolio` 포트폴리오 | 회고를 바깥 사람이 읽을 글로 고친다 | 같은 글의 Notion 판(4장) |
| `trim` CLAUDE.md 정리 | 꼭 지킬 규칙만 짧게 남기고 상세는 docs로 옮겨 가리킨다 | diff, 옮긴 규칙의 목적지 표 |
| `loss` 압축 손실 반영 | 압축 손실 점검 결과(예: `log/runshoes_compaction_loss_20261105.md`)에서 살릴 것을 CLAUDE.md · docs · 메모리에 넣자고 제안한다 | 제안 diff. 뒤집힌 결정은 넣지 않는다 |
| `polish` 인계 요약 다듬기 | 세션이 쓴 요약을 원문(트랜스크립트)과 맞대 빠진 결정 · 틀린 사실을 고친다 | 요약의 새 판(`summary`의 새 행, 옛것은 남긴다) |

## 2. 언제 일하나

**권하는 방식: 사람이 시킨다 + 브리지가 "할 일"을 알려 준다. 자동 실행은 마지막 단계에서 하나만.**

1. **사람이 시킨다(12a부터).** 포먼 창에 "오늘 회고 써 줘" · "CLAUDE.md 정리해 줘"라고 하면 디스패처가 역할 `scribe` · 일감 · 기간을 계획에 담는다. 서기 캐릭터를 눌러도 일감을 고를 수 있다.
2. **브리지가 할 일을 센다(12d).** LLM 없이 기계적으로 센다. 서기 머리 위에 "할 일 3"처럼 뜨고, 누르면 그 일감이 계획 카드로 채워진다.
   - 코드 커밋은 쌓였는데 README · `log/`는 그 뒤로 안 바뀜(예: 커밋 10개 이상)
   - 로드맵 단계에 결과 파일(`log/stage<N>_*`)이 없음
   - CLAUDE.md가 기준 줄 수(예: 80줄)를 넘음
   - 새 인계 요약이 생김(`polish` 후보), 압축 손실 점검 결과가 생김(`loss` 후보)
   - 하루가 끝남(마지막 커밋 뒤 2시간 조용함 → `retro` 후보)
3. **자동 실행(12d 끝, 써 본 뒤).** 하루 끝 회고 **초안**만 자동으로 띄운다. 브랜치에 쌓이기만 하고 합치기는 사람이 한다.

**커밋 수로 자동 실행하지 않는 이유:** 문서는 사람이 읽는 글이라 초안이 쌓이면 검토 빚이 된다. 또 같은 저장소에 일하는 세션이 있으면 README에서 충돌이 난다. 그래서 할 일은 세고, 실행은 사람이 누른다.

**어떻게 도나:** 실제 CC 세션이다(`claude -p` 한 번이 아니다). 여러 파일을 읽고 diff를 만들어야 해서다.
- 11단계 worktree로 띄운다(`.worktrees/scribe-<날짜>`, 브랜치 `cc/scribe-…`)
- **[합치기]가 곧 사람의 검토 관문이다.** 이미 있는 장치를 그대로 쓴다
- 예외는 `polish`다. 작아서 디스패처처럼 `claude -p` 한 번으로 돈다

## 3. 무엇을 읽나 — 재료 묶음

브리지가 LLM 없이 **재료 묶음**(디스패처의 상황 묶음과 같은 방식)을 만들어 첫 글에 넣는다. 서기는 거기서 시작해 필요한 원문만 더 읽는다.
- 숨긴 세션(0018 `hidden_at`)은 뺀다
- 모든 글은 Masker를 거친다(비밀값)

| 출처 | 읽는 것 | 왜 |
|---|---|---|
| `turn.prompt_text`(origin human) | 사람이 한 말 — 지시 · 결정 · 정정 | 회고의 뼈대. "무엇을 왜 바꿨나"가 여기 있다 |
| `git_commit` · `build` | 커밋 메시지 · 해시 · 빌드 성패 | 실제로 들어간 것. 근거 표시의 기준 |
| `dispatch`(`plan` ↔ `edited`) | 포먼이 낸 계획과 사람이 고친 것 | AI가 틀리고 사람이 바로잡은 자리 |
| `approval` | 묻고 · 거절된 도구 호출과 사유 | 사람이 멈춘 순간 |
| `summary` · `session_action` | 인계 · 끝내기 · 합치기 · 버리기 | 세션 사이의 이음새 |
| `message` 토큰 · `event` 수 | 세션 · 하루별 토큰, 도구 사용 수 | 숫자(비용 · 규모) |
| `character_session` | 세션 제목 · 역할 · worktree · 기간 | 누가 무엇을 했나 |
| 저장소 | `log/` · `docs/` · README · CLAUDE.md · `git diff --stat` | 이미 쓴 기록. 다시 쓰지 않고 가리킨다 |
| 트랜스크립트(`transcript_file.path`) | 턴마다 마지막 답의 본문만 골라 읽는다 | DB에는 답 본문이 없다(토큰 · 이벤트만) |

**오늘(11-05) 포먼 프로젝트의 양:**
- 사람 턴 34개(9.3만 자)
- 커밋 32개
- 디스패치 4건
- log · docs 전체 56만 자
- 이 세션 트랜스크립트 94MB. 대부분 도구 결과라 그대로 넣지 않는다

## 4. 수준을 어떻게 담보하나

사람이 읽는 글이라 **사실이 맞는가**와 **읽을 만한가**를 나눠 막는다.

**사실을 맞추는 장치(기계로 확인):**
1. **모든 주장에 근거를 단다.** 문장 끝에 `[c:e223f2e]`(커밋) · `[t:4521]`(턴) · `[log:stage11_roles_result.md]` 같은 표시를 붙인다.
2. **브리지가 근거를 확인한다.** LLM 없이 본다.
   - 해시 · 턴 · 파일이 실제로 있는가
   - 글에 쓴 숫자(커밋 수 · 토큰 · 개수)가 DB 값과 맞는가
   - 틀린 것이 있으면 합치기 전에 패널에 띄운다
   - 바깥에 낼 판(Notion)에서는 표시를 각주로 바꾸거나 뺀다
3. **점검 역할이 읽는다.** 초안을 점검(inspector, 읽기 전용) 세션이 원문과 맞대 다음을 짚는다.
   - 근거 없는 주장
   - 뒤집힌 결정을 지금 것처럼 쓴 곳
   - 빠진 실수
   - 비용은 1.5배가 된다. `retro` · `portfolio` · `trim`에만 쓴다

**읽을 만하게 하는 장치:**
4. **문체 기준 문서**(`docs/style_guide.md`, 12a에서 만든다). 이미 있는 사용자 지시를 모은다.
   - 결과 문서에는 한 일 · 조사 결과 · 설계와 달랐던 점 · 판단 근거만 쓰고 브리프를 다시 쓰지 않는다
   - 화면 글은 "~습니다"로 쓴다
   - CLAUDE.md는 금지 · 결정만 짧게 쓰고 상세는 docs를 가리킨다
   - 금지할 것도 적는다: 과장("혁신적"), 근거 없는 수치, 일반론 회고("소통이 중요했다")
5. **잘 쓴 본보기를 넣는다.** 사용자가 받아들인 글을 본보기로 첫 글에 붙인다. 예: `log/runshoes_compaction_loss_20261105.md`, `log/runshoes_claude_md_draft_20261105.md`.
6. **사람이 고친 양을 잰다.** 합치기 전에 사람이 브랜치에서 고친 줄 수와 일감 종류를 남긴다(`dispatch.edited`와 같은 생각).
   - 고친 양이 줄어드는지가 수준의 지표다
   - 이 숫자가 12d 자동 실행을 열지 정하는 기준이다

**사람의 몫:** [합치기] 전 diff 확인. Notion에 올리는 것은 따로 [게시] 버튼을 누를 때만.

## 5. Notion 연동

- **원본은 git(마크다운), Notion은 게시판이다.** 서기는 저장소에 먼저 쓰고, 합쳐진 글만 Notion에 올린다. 고치는 것도 저장소에서 하고 다시 게시한다.
- **연결:** claude.ai 계정의 Notion 커넥터가 이미 붙어 있다(`claude mcp list` → `claude.ai Notion … ✔ Connected`, 11-05). 서기 세션은 같은 로그인이라 따로 토큰이 필요 없다.
- **막을 것:**
  - 서기 세션의 Notion 도구는 페이지 만들기 · 고치기 · 읽기만 허용하고, 지우기 · 옮기기 · 공유 변경은 거부한다(approval.toml)
  - 정해 둔 부모 페이지(예: "FOREMAN 포트폴리오") 아래에만 쓴다
- **모양:**
  - 부모 페이지 아래 프로젝트 페이지
  - 그 아래 회고 · 포트폴리오 글
  - "작업 기록" 데이터베이스 하나(날짜 · 프로젝트 · 단계 · 커밋 수 · 토큰 · 링크)
- **다시 올리기:** 게시한 페이지 id를 DB(`doc_publish`)에 남겨, 같은 글을 다시 올리면 새로 만들지 않고 고친다.
- **확인 안 된 것:**
  - 헤드리스 세션에서 커넥터 쓰기가 되는지(시험 페이지 하나로 확인 — 사용자 승인 뒤)
  - 안 되면 Notion API 통합 토큰(`.env.notion`)으로 브리지가 직접 올린다

## 6. 토큰

**오늘(11-05) 실측:**
- 포먼 프로젝트 Opus 출력 150만 · 캐시 읽기 5.1억 · 캐시 쓰기 366만 토큰
- 런슈즈 출력 68만
- 디스패처 1회: 상황 1.1만 자, 17초

**일감 하나의 어림:**

| 일감 | 입력 | 출력 | 모델 |
|---|---|---|---|
| `retro` 하루(포먼 11-05 규모) | 재료 묶음 4~6만 자 + 파일 읽기 → 15~25만 토큰(캐시 포함) | 1~2만 | Opus(사람이 읽는 글) |
| 위 + 점검 | +50% | +0.5만 | Opus |
| `sync` | 5~10만 | 0.5~1만 | Sonnet |
| `trim` · `loss` | 10~20만 | 1만 | Opus |
| `polish` | 요약 + 원문 일부 2~4만 | 0.3만 | Sonnet, `claude -p` |

- 하루 회고 한 번이 오늘 포먼 출력의 **1~2%** 정도다
- 서기도 보통 세션이라 쓴 토큰이 서기 카드에 그대로 잡힌다(따로 셀 것이 없다)
- 상한: 일감마다 턴 상한, 재료 묶음 글자 상한(넘으면 오래된 것부터 줄이고 줄였다고 적는다)

## 7. 포트폴리오 관점 — 이것 자체가 작품이다

"AI가 작업 과정을 읽고 회고를 쓴다"를 보여 주려면 **회고 글보다 회고가 만들어지는 길**이 작품이다.

```
CC 세션들 ─hook·트랜스크립트→ 브리지 ─→ DB(턴 · 커밋 · 승인 · 디스패치 · 토큰)
                                           │ 기계적 재료 묶음(비밀값 가림)
                                           ▼
                                  서기 초안(문장마다 근거 표시)
                                           │ 근거 확인(기계) → 점검 역할 검토(AI)
                                           ▼
                                  사람 [합치기] — 고친 양을 잰다
                                           │ [게시]
                                           ▼
                                       Notion 포트폴리오
```

**보여 줄 수 있는 것:**
- 근거가 달린 글
- 기계 확인과 AI 검토의 분업
- 사람이 고친 양이 시간이 갈수록 주는 그래프
- 일감마다 쓴 토큰

**조심할 것:** AI 회고는 쉽게 밋밋해진다("소통이 중요했다"). 읽는 사람이 보고 싶은 것은 **판단**이다.
- 그래서 재료 묶음은 사람이 정정한 곳 · 거절한 승인 · 뒤집힌 결정 · 실수를 앞에 둔다
- 오늘 것으로는 다음이 있다:
  - 영어 진행 글을 hook으로 잡은 일
  - '푸른 고래' 오해
  - 테마와 DB의 역할 이름이 달라 색이 한 번도 안 맞던 것
  - 미분류를 13개로 잘못 센 것(실제 12)
- 이 데이터는 이 시스템만 가진 것이다

## 8. 첫 재료 — FOREMAN 11-05

첫 일감은 **FOREMAN의 11-05 하루 회고**로 한다.
- 정답을 사용자와 이 세션이 알고 있어 수준을 재기 좋다
- 재료: 커밋 32개, 10d 마법학교 테마 → 11 인계 · 디스패처 · worktree · 재배치, 사람 턴 34개, log 결과 파일 6개
- **이 세션은 여러 번 압축됐다.** 회고 전에 런슈즈처럼 압축 손실 점검을 이 세션에도 돌리면 `loss` 일감의 시험도 된다
