# 12 — 서기(문서화 캐릭터) 설계 (2026-11-05 초안, 사용자 확인 대기)

README 로드맵 12는 원래 "떠돌이 포트폴리오 작성 캐릭터"였다. 11-05 사용자 결정으로 **프로젝트마다 하나씩 두는 문서 담당**으로 바꿨다. 포트폴리오는 이 캐릭터가 하는 일 중 하나다.

## 1. 누구인가

| 항목 | 정한 것 |
|---|---|
| 역할 이름 | `scribe` — 화면 이름 **서기**. coder(코더) · inspector(점검) · cicd(CI/CD)와 같은 층위 |
| 캐릭터 | 프로젝트마다 "서기" 하나. 부모 = 그 프로젝트의 포먼, `spawned_by = foreman`(0017의 코더 · 점검과 같은 방식) |
| 색 | 잉크 갈색 `#b0713a` — 금색(포먼) · 파랑 · 초록 · 보라와 겹치지 않는다 |
| 상주 자리 | 테마의 `library` 구역 — 마법학교 "서고", 오피스 "아카이브". 현장은 `store`(자재창고) 대신 도면함을 둘 자리를 정한다. plain은 구역이 없어 하나 더한다 |
| 움직임 | 일이 없으면 서고에 앉아 있다(IDLE). 일하면 서고 책상에서 쓰고, 커밋할 때 커밋 데스크로 간다. 지금도 서고는 "파일 읽기" 일이 가는 곳이라 따로 만들 것이 적다 |

**맡는 일(일감 종류):**

| 일감 | 하는 것 | 내놓는 것 |
|---|---|---|
| `sync` 문서 맞추기 | 마지막 문서 갱신 뒤의 커밋 · log를 보고 README 로드맵 줄 · docs를 고친다 | 브랜치의 diff |
| `retro` 회고 | 기간(하루 · 단계)을 정해 한 일 · 판단 · 뒤집힌 결정 · 실수 · 숫자를 쓴다 | `log/retro_<날짜>_<주제>.md` |
| `portfolio` 포트폴리오 | 회고를 바깥 사람이 읽을 글로 고친다 | 같은 글의 Notion 판(4장) |
| `trim` CLAUDE.md 정리 | 꼭 지킬 규칙만 짧게 남기고 상세는 docs로 옮겨 가리킨다 | diff, 옮긴 규칙의 목적지 표 |
| `loss` 압축 손실 반영 | 압축 손실 점검 결과(예: `log/runshoes_compaction_loss_20261105.md`)에서 살릴 것을 CLAUDE.md · docs · 메모리에 넣자고 제안한다 | 제안 diff. 뒤집힌 결정은 넣지 않는다 |
| `polish` 인계 요약 다듬기 | 세션이 쓴 요약을 원문(트랜스크립트)과 맞대 빠진 결정 · 틀린 사실을 고친다 | 요약의 새 판(`summary`의 새 행, 옛것은 남긴다) |
| `later` 나중에 할 일 정리(11-06 사용자) | 대화에서 "이건 나중에 하자"고 한 것을 모아 README 「나중에 할 일 (정해 두고 미룬 것)」 표에 넣는다 — 무엇 · 언제 · 조건 · 근거. 이미 한 것은 표에서 뺀다 | README 표 diff. 예: 11-06 Codex 연동(쓸 데 둘 · Sonnet 먼저 비교) |

## 2. 언제 일하나

**권하는 방식: 사람이 시킨다 + 브리지가 "할 일"을 알려 준다. 자동 실행은 마지막 단계에서 하나만.**

1. **사람이 시킨다(12a부터).** 포먼 창에 "오늘 회고 써 줘" · "CLAUDE.md 정리해 줘"라고 하면 디스패처가 역할 `scribe` · 일감 · 기간을 계획에 담는다. 서기 캐릭터를 눌러도 일감을 고를 수 있다.
2. **브리지가 할 일을 센다(12d).** LLM 없이 기계적으로 센다. 서기 머리 위에 "할 일 3"처럼 뜨고, 누르면 그 일감이 계획 카드로 채워진다.
   - 코드 커밋은 쌓였는데 README · `log/`는 그 뒤로 안 바뀜(예: 커밋 10개 이상)
   - 로드맵 단계에 결과 파일(`log/stage<N>_*`)이 없음
   - CLAUDE.md가 기준 줄 수(예: 80줄)를 넘음
   - 새 인계 요약이 생김(`polish` 후보), 압축 손실 점검 결과가 생김(`loss` 후보)
   - 하루가 끝남(마지막 커밋 뒤 2시간 조용함 → `retro` 후보)
3. **자동 실행(12d 끝, 써 본 뒤).** 하루 끝 회고 **초안**만 자동으로 띄운다. 브랜치에 쌓이기만 하고 합치기는 사람이 한다.

**커밋 수로 자동 실행하지 않는 이유:** 문서는 사람이 읽는 글이라 초안이 쌓이면 검토 빚이 된다. 또 같은 저장소에 일하는 세션이 있으면 README에서 충돌이 난다. 그래서 할 일은 세고, 실행은 사람이 누른다.

**어떻게 도나:** 실제 CC 세션이다(`claude -p` 한 번이 아니다). 여러 파일을 읽고 diff를 만들어야 해서다.
- 11단계 worktree로 띄운다(`.worktrees/scribe-<날짜>`, 브랜치 `cc/scribe-…`)
- **[합치기]가 곧 사람의 검토 관문이다.** 이미 있는 장치를 그대로 쓴다
- 예외는 `polish`다. 작아서 디스패처처럼 `claude -p` 한 번으로 돈다

## 3. 무엇을 읽나 — 재료 묶음

브리지가 LLM 없이 **재료 묶음**(디스패처의 상황 묶음과 같은 방식)을 만들어 첫 글에 넣는다. 서기는 거기서 시작해 필요한 원문만 더 읽는다.
- 숨긴 세션(0018 `hidden_at`)은 뺀다
- 모든 글은 Masker를 거친다(비밀값)

| 출처 | 읽는 것 | 왜 |
|---|---|---|
| `turn.prompt_text`(origin human) | 사람이 한 말 — 지시 · 결정 · 정정 | 회고의 뼈대. "무엇을 왜 바꿨나"가 여기 있다 |
| `git_commit` · `build` | 커밋 메시지 · 해시 · 빌드 성패 | 실제로 들어간 것. 근거 표시의 기준 |
| `dispatch`(`plan` ↔ `edited`) | 포먼이 낸 계획과 사람이 고친 것 | AI가 틀리고 사람이 바로잡은 자리 |
| `approval` | 묻고 · 거절된 도구 호출과 사유 | 사람이 멈춘 순간 |
| `summary` · `session_action` | 인계 · 끝내기 · 합치기 · 버리기 | 세션 사이의 이음새 |
| `message` 토큰 · `event` 수 | 세션 · 하루별 토큰, 도구 사용 수 | 숫자(비용 · 규모) |
| `character_session` | 세션 제목 · 역할 · worktree · 기간 | 누가 무엇을 했나 |
| 저장소 | `log/` · `docs/` · README · CLAUDE.md · `git diff --stat` | 이미 쓴 기록. 다시 쓰지 않고 가리킨다 |
| 트랜스크립트(`transcript_file.path`) | 턴마다 마지막 답의 본문만 골라 읽는다 | DB에는 답 본문이 없다(토큰 · 이벤트만) |

**사람 말은 자르지 않고 다 준다**(11-10 사용자, dispatch #209) [log:scribe_material_noclip_20261110.md] [log:merge_scribe_noclip_20261110.md] [log:note_threads_only_20261113.md]
- 재료의 사람 말(`turn.prompt_text`)은 `<pasted_content>` 껍데기만 벗기고 글자를 빼지 않는다(`bridge/scribe.py` `_full`). 길이는 껍데기 벗기기로만 줄인다
- 「턴 번호만 주고 서기가 DB를 읽게」 하는 길은 안 쓴다
  - 서기가 저장소 밖 재료만 읽는다는 약속이 깨진다
  - 읽을지가 서기 판단에 달려 또 조용히 빠진다
- 자르는 칸은 요약 줄뿐이다(후보 목록 300자 · 디스패치 요청 200자 · 계획 · 고친 것 400자 · 승인 대상 120자 · 사유 160자, `_clip`). 줄 앞에 `[t:…]` · `디스패치 #…` · `승인 #…`이 먼저 와서 잘려도 원문 번호는 남는다
- 상한을 두지 않은 근거: 11-10 사람 턴 가장 긴 것이 1.8만 자(petmint)로 서기가 쪽을 나눠 읽을 수 있다. 상한을 두면 같은 잘림이 다시 생긴다
- 2,000자 넘는 한 줄은 Read가 조용히 자르므로 `LINE_WRAP = 1500`자마다 줄만 나눈다(글자는 그대로). 「나중에 할 일 정리」 재료(`scribe_room.py` `later_material`)도 같다

**오늘(11-05) 포먼 프로젝트의 양:**
- 사람 턴 34개(9.3만 자)
- 커밋 32개
- 디스패치 4건
- log · docs 전체 56만 자
- 이 세션 트랜스크립트 94MB. 대부분 도구 결과라 그대로 넣지 않는다

## 4. 수준을 어떻게 담보하나

사람이 읽는 글이라 **사실이 맞는가**와 **읽을 만한가**를 나눠 막는다.

**사실을 맞추는 장치(기계로 확인):**
1. **모든 주장에 근거를 단다.** 문장 끝에 `[c:e223f2e]`(커밋) · `[t:4521]`(턴) · `[log:stage11_roles_result.md]` 같은 표시를 붙인다.
2. **브리지가 근거를 확인한다.** LLM 없이 본다.
   - 해시 · 턴 · 파일이 실제로 있는가
   - 글에 쓴 숫자(커밋 수 · 토큰 · 개수)가 DB 값과 맞는가
   - 틀린 것이 있으면 합치기 전에 패널에 띄운다
   - 바깥에 낼 판(Notion)에서는 표시를 각주로 바꾸거나 뺀다
3. **점검 역할이 읽는다.** 초안을 점검(inspector, 읽기 전용) 세션이 원문과 맞대 다음을 짚는다.
   - 근거 없는 주장
   - 뒤집힌 결정을 지금 것처럼 쓴 곳
   - 빠진 실수
   - 비용은 1.5배가 된다. `retro` · `portfolio` · `trim`에만 쓴다

**읽을 만하게 하는 장치:**
4. **문체 기준 문서**(`docs/style_guide.md`, 12a에서 만든다). 이미 있는 사용자 지시를 모은다.
   - 결과 문서에는 한 일 · 조사 결과 · 설계와 달랐던 점 · 판단 근거만 쓰고 브리프를 다시 쓰지 않는다
   - 화면 글은 "~습니다"로 쓴다
   - CLAUDE.md는 금지 · 결정만 짧게 쓰고 상세는 docs를 가리킨다
   - 금지할 것도 적는다: 과장("혁신적"), 근거 없는 수치, 일반론 회고("소통이 중요했다")
5. **잘 쓴 본보기를 넣는다.** 사용자가 받아들인 글을 본보기로 첫 글에 붙인다. 예: `log/runshoes_compaction_loss_20261105.md`, `log/runshoes_claude_md_draft_20261105.md`.
6. **사람이 고친 양을 잰다.** 합치기 전에 사람이 브랜치에서 고친 줄 수와 일감 종류를 남긴다(`dispatch.edited`와 같은 생각).
   - 고친 양이 줄어드는지가 수준의 지표다
   - 이 숫자가 12d 자동 실행을 열지 정하는 기준이다

**사람의 몫:** [합치기] 전 diff 확인. Notion에 올리는 것은 따로 [게시] 버튼을 누를 때만.

## 5. Notion 연동

- **원본은 git(마크다운), Notion은 게시판이다.** 서기는 저장소에 먼저 쓰고, 합쳐진 글만 Notion에 올린다. 고치는 것도 저장소에서 하고 다시 게시한다.
- **연결(11-06 사용자 결정 — 길 B):** 서기 세션이 Notion에 쓰지 않는다. 브리지가 Notion API로 직접 올린다(`bridge/notion.py`, 내부 통합 토큰 `.env.notion`). "권한을 코드가 아니라 구조로 막는 게 맞고, LLM이 17KB를 옮겨 적다가 바꿀 위험도 없고"(사용자) [log:stage12_scribe_result.md]. ~~claude.ai Notion 커넥터로 서기 세션이 쓴다(11-05 초안)~~
- **막을 것 — 권한은 Notion이 막는다:**
  - 통합은 「프로젝트」 페이지에만 연결한다(11-06엔 FOREMAN 페이지만, 11-09 「프로젝트」로 넓힘). 연결 밖 페이지는 통합이 읽지도 못한다(404 — 코드를 우회해 휴지통 요청을 보내도 Notion이 거부, 11-06 실제 확인)
  - 게시기는 프로젝트마다 `config/notion.toml`의 root 아래만 고친다(`Scope`). 사람이 만든 페이지(「인프라」 · 이력서 등)는 건드리지 않는다
- **모양:**
  - 부모 페이지 아래 프로젝트 페이지
  - 그 아래 회고 · 포트폴리오 글
  - "작업 기록" 데이터베이스 하나(날짜 · 프로젝트 · 단계 · 커밋 수 · 토큰 · 링크) — **아직 없다**(12c 남은 것)
  - ~~**11-06 사용자 결정:** 루트(FOREMAN - AI 에이전트 관제실) 바로 아래에 포트폴리오 8편만, 묶음 페이지 없이~~ (11-09 바뀜 → 아래) 번호 붙은 제목("00 한눈에 — …", 번호는 `config/portfolio.toml` slug)으로 번호순. 회고는 Notion에서 내리고 git에만 둔다(바깥 판은 포트폴리오가 맡는다). 실제 게시는 브리지가 API로 직접(`bridge/notion.py`, 길 B)
  - **지금(11-09 사용자 결정):** 통합은 「프로젝트」 페이지에 연결. 그 아래 프로젝트마다 페이지 하나, 그 아래 **[기술문서]**(`docs/*.md`) · **[포트폴리오]**(`portfolio/*.md`, 번호순). 「인프라」 폴더(사람이 쓴 인프라 문서 넷)는 게시기가 다루지 않는다. 페이지 id · 기준 커밋 · 기술문서 방식은 `config/notion.toml`
    ```
    프로젝트
    ├ RUNSHOES-러닝화 스펙·리뷰 아카이브  ├ [기술문서] (자동 — docs 16편)  └ [포트폴리오]
    ├ 펫퍼민트 반려동물 보험약관 안내 챗봇  ├ [기술문서] (사람이 옮긴 사본에 맞춤 — 자동, 맨 뒤 번호 새 페이지만 만듦, 11-09)  └ [포트폴리오]
    ├ FOREMAN - AI 에이전트 관제실         ├ [기술문서] (꺼짐)  └ [포트폴리오] (10편, 사람이 [게시])
    └ 인프라
    ```
- **git이 원본, 사람이 Notion에서 고친 블록은 덮지 않고 알린다(11-09 사용자 결정).** 게시기는 블록을 내용으로 짝지어 바뀐 자리만 고치지만, 견주는 상대가 "지금 Notion"이라 사람이 고친 블록도 git 내용으로 되돌렸다(실험: 고친 문단은 되돌아가고 더한 메모는 지워짐, 알림 없음 — "git과 Notion이 조용히 갈라진다"). 이제 덮기 전에 마지막으로 고친 쪽(`last_edited_by`)이 우리 봇이 아니고 글이 새 원본과 다른 블록을 찾아, 있으면 그 파일은 멈추고(`HumanEdited`) 텔레그램 · 서기 할 일로 알린다. 그 수정을 git에 옮기면 글이 같아져 풀리고, 버리려면 [Notion 수정 버리고 덮기]. mermaid 코드는 뺀다(미리보기만 바꿔도 사람이 고친 것이 된다). "수정: …"을 덧붙이는 방식은 쓰지 않는다
  - 11-12 고침: 맞추기는 글이 같은 블록(kept)을 손대지 않아 마지막 수정자가 처음 쓴 사람으로 남는다 → git에서 그 문단만 고쳐도 사람 수정으로 잘못 보았다(인프라 09). 이제 **지난번 올린 git 판(짝 `commit_sha`)의 블록과 글이 같으면 사람 수정이 아니다.** `commit_sha`가 없는 짝(처음 짝지은 페이지)이나 그 판을 못 읽으면 옛 판정 그대로 [log:notion_publish_three_20261112.md]
  - **force(「Notion 수정 버리고 덮기」)는 그 프로젝트 서기실에서 사람이 누른다 — 관리자를 거쳐 전달하지 않는다(11-12 사용자 결정).** 한 쪽 게시(`POST /api/publish`)가 사람 수정으로 멈출 때도 [지금 맞추기]처럼 서기 할 일에 덮기 줄 · 단추와 텔레그램 ✋를 남긴다(`DocSync.hold/release` — 같은 자리라 한 파일에 줄이 둘 생기지 않는다). 프로젝트 토큰은 force · [지금 맞추기] 한꺼번에를 부를 수 없다. 그 전엔 인프라(`docs = "manual"`)가 한 쪽 게시로만 올려 덮기 단추가 안 떠, force 하나에 관리자를 거쳐 메시지가 네 번 오갔다 [log:notion_onesided_hold_20261112.md]
- **게시 설정을 프로젝트 저장소로 · 프로젝트 토큰으로 게시(11-12, `bridge/notioncfg.py`):** `<저장소>/.foreman/notion.toml`이 그 저장소 `origin/main`에 있으면 `docs` · `skip` · `title` 등(`REPO_KEYS`)은 모두 그 파일 것, 없으면 지금처럼 `config/notion.toml`. `root` · `docs_page` · `portfolio_page` · `github` · `ref`는 FOREMAN에서만(저장소 파일에 있으면 쓰지 않고 경고). 맞추기 주기(5분)마다 다시 읽고, 깨지면 옛 설정 그대로 + 텔레그램. 프로젝트 토큰은 자기 프로젝트 `POST /api/publish`(force · `docsync`는 관리 토큰만) · `GET /api/publish?project=`(지금 설정의 출처 `config`) · 짝 등록 `POST /api/publish/pair`
  - **저장소 파일을 잃으면 게시를 멈춘다(11-12 사용자 지시).** 한 번이라도 저장소 파일로 돈 프로젝트는 `.run/notion_repo_config.json`에 기억한다(브리지를 다시 띄워도 남는다). 그 파일을 잃으면(지워짐 · 브리지를 다시 띄운 뒤 깨짐) FOREMAN 칸으로 떨어지지 않고 멈춘다 — 한 쪽 게시 · 짝 등록 · [지금 맞추기] · 자동을 모두 거절하고, 텔레그램 · `config.halted` · 서기 할 일 줄로 알린다. 파일이 돌아오면 다시 돌고 알린다. 저장소 파일을 읽는 기준은 그 프로젝트 FOREMAN 칸의 `ref`. 일부러 FOREMAN 칸으로 되돌릴 때는 관리 토큰으로 `DELETE /api/publish/repo-config?project=`. 까닭: FOREMAN 칸이 비어 있으면(인프라 11-12 — 저장소 몫 칸을 지움) 막아 둔 `create = false` · `archive = false` · `order = "keep"`이 풀린 채 알림 없이 돌 수 있었다 [log:notion_repo_config_halt_20261112.md]
- **기술문서 자동 맞추기(11-09, `bridge/docsync.py`):** 기준은 push된 `origin/main`(Notion은 GitHub의 사본). docs 커밋 뒤 30분 조용하면 바뀐 파일만(지문 비교) 갈아 끼우고, 지워진 원본은 휴지통(`archive = false`이거나 `create = false`인 프로젝트는 휴지통으로 보내지 않고 실패로 남긴다 — 11-09, 경로만 바뀐 것이면 짝을 새 경로로 옮기면 풀린다), 차례는 `docs/README.md` 표 순서. 제목은 "파일 이름 — README 표 설명 앞부분"(런슈즈 docs는 H1이 없다). 프로젝트 칸에 `title = "h1"`(11-12, 인프라 요청)이면 제목은 문서의 첫 H1 줄이고(바뀌면 Notion 제목도 따라 바뀐다), H1이 없는 문서만 옛 방식으로 돌아간다 — 규칙은 `config/notion.toml` 머리 주석. 뒤처짐(커밋 N · 파일 M)은 서기 할 일에 프로젝트마다 한 줄, 실패 · 사람 수정은 텔레그램. 대상: `docs/` 아래 하위 폴더까지(`docs/**/*.md`, 11-09 — ~~`docs/` 바로 아래만~~), `docs/archive/`는 늘 빼고, 프로젝트 `skip`의 "…/"는 그 폴더 통째로 뺀다(펫퍼민트 `docs/ops/`) [log:petmint_docs_move_20261109.md]. 포트폴리오는 지금처럼 사람이 [게시]
- **펫퍼민트 — 사람이 옮겨 둔 페이지에 맞추기(11-09 사용자 결정, `config/notion.toml` 펫퍼민트 칸):** ~~새 페이지를 만들지 않고(`create = false`)~~(11-09 16:51 바뀜 → 아래 「새 문서 만들기」), 제목 · 자리 · 차례는 그대로, 사본 상자 대신 맨 아래 갱신 한 줄. 비교는 **쪽 단위 글**(`keep_notion` `"shape"`) — 꾸밈 · 체크박스 표시 · 공백 · 줄바꿈 · 블록 나눔 · 제목 단계 · 코드 언어를 빼고 글만 견준다. 글이 같으면 Notion은 손대지 않고, Notion이 지난번 맞춘 git과 같으면 git 변경만 맞추고(글이 같은 블록은 Notion 모양 그대로), 그 밖은 멈추고 알린다 [log:petmint_docsync_dryrun_20261109.md]
  - git만 바뀌었을 때는 **바뀐 블록만** 고친다(`shape_patch`) — 지난 git ↔ 새 git에서 글이 바뀐 맨 위 블록을 같은 글의 Notion 블록에서 찾아 그 자리에서 글만 바꾸고(블록 종류는 Notion 것), 빠진 블록은 지우고 새 블록은 앞 블록 뒤에 끼운다. 짝이 하나로 안 맞으면(그 글의 Notion 블록이 없거나 여럿 · 빈 블록 · 표 · 그림 · 안쪽 목록 · 맨 앞 끼우기) 아무것도 쓰기 전에 멈추고 알린다. 지난 글은 git 이름 바꾸기 기록의 옛 경로로 읽는다(파일을 옮겨도 이어진다)
  - **잃는 것:** 사람이 Notion에서 **모양만** 고친 것(굵게 · 제목 단계 · 줄 나눔 · 체크박스 체크 등)은 사람 수정으로 잡히지 않는다. 글이 같은 동안은 덮지 않으니 남는다. **git에서 그 블록의 글이 바뀌면 그 블록의 글(꾸밈 포함)은 git 것으로 바뀐다** — 그 블록에 사람이 해 둔 꾸밈(굵게 · 링크 등)은 알림 없이 사라질 수 있다. 블록 종류(제목 단계 · to_do 등)와 바뀌지 않은 다른 블록은 그대로다. 글을 고친 것은 여전히 잡는다
  - 글자 자체가 바뀌는 변환(마침표 넣기 · 기호 바꾸기)이 새로 생기면 멈춘다 — 실제 글 차이라 맞는 쪽이다
  - **새 문서 만들기 — `create = true`(11-09 16:51:18 KST 켬, 사용자 — 모의 실행에서 17 만듦 · 05-1 실패를 본 뒤)** [log:petmint_create_prep_20261109.md] [log:credits_and_middle_number_20261109.md]. 아래 옵션은 모두 펫퍼민트 칸에만 있다(없으면 런슈즈 · FOREMAN처럼 기본 동작)
    - `new_parent = "folder"` — `docs/<폴더>/x.md` 새 문서는 같은 폴더의 게시된 형제들이 모두 걸린 부모 페이지 아래(`docs/02_pipeline/` → 「02. 파이프라인 설계」). 형제가 없거나 부모가 여럿이면 만들지 않고 실패
    - `new_title = "numbered"` — 번호는 파일 이름(`17_` → "17", `03a_` → "03-1"), 이름은 부모 페이지의 원본 문서(`pipeline.md`)에서 그 번호로 시작하는 **마지막** 줄(「7. 단계별 문서」가 앞쪽 목록보다 짧다). 펫퍼민트 docs엔 H1이 없어 이름을 다른 데서 가져올 수 없다. 번호 · 이름을 못 정하면 만들지 않고 실패 — 상위 폴더 문서(`docs/03_extra.md`처럼)는 이름을 정할 원본 문서가 없어 실패
    - **중간 번호는 만들지 않고 실패로 남긴다**(사용자) — Notion은 새 하위 페이지를 부모 **끝**에 붙이고 API로 자리를 정할 수 없다. 새 문서 번호(`notion.file_order` — `17_` → (17, 0), `03a_` → (3, 1))가 같은 폴더 게시된 형제 중 가장 큰 번호보다 작으면 "중간 번호라 자리를 정할 수 없습니다. 직접 만드십시오 — <경로>(같은 폴더 마지막 번호 16)". 맨 뒤 번호만 만든다. 지운 문서의 페이지도 남아 있으니(휴지통 안 보냄) 그 번호도 "마지막 번호"에 든다. 이 사유는 알림에 "OutOfScope:" 없이 글 그대로 간다
    - `order = "keep"`을 둔 까닭 — 중간 번호 페이지의 차례를 다시 세우려면 그 부모 아래 18쪽을 모두 옮겨야 하고, 옮기면 「02」 본문 7절 안에 있던 하위 페이지 자리도 모두 끝으로 간다. 그래서 자리 · 차례는 사람이 둔 그대로 둔다. 새 페이지 링크는 「02」 본문 맨 아래(꼬리 줄 뒤)에 생긴다
    - `archive = false` — 원본이 사라져도 휴지통으로 보내지 않고 실패로만(`create`와 따로, 사람이 보고 판단). 기본값 true(런슈즈 그대로)
    - `headings = "md"` — 제목 단계를 마크다운 그대로(`##` → heading_2 · `###` → 3 · `####` 이상 → 4, 사람이 옮긴 페이지 모양). 새 페이지뿐 아니라 git만 바뀌어 끼우는 블록(`shape_patch`)도 같은 변환. 비교는 글만 보므로 기존 20쪽 맞추기 결과는 같다
    - 목록 문서(`pipeline.md`)의 목록 줄이 새 하위 페이지 제목과 같으면 글 비교에서 빠진다 — 본문에 "17. …" 글 블록을 따로 끼우지 않고 꼬리 줄만 고친다
    - **heading_4 만들기는 아직 확인 안 됨** — 사람이 옮긴 페이지에 heading_4 블록이 있어 Notion이 아는 종류지만, 우리 통합이 만들 수 있는지는 펫퍼민트가 `####`가 든 새 문서 · 절을 push해 처음 쓸 때 안다. 안 되면 그 파일이 실패로 남고 텔레그램으로 온다(조용히 넘어가지 않음)
- **다시 올리기:** 게시한 페이지 id를 DB(`doc_publish`)에 남겨, 같은 글을 다시 올리면 새로 만들지 않고 고친다.

## 7. 포트폴리오 관점 — 이것 자체가 작품이다

"AI가 작업 과정을 읽고 회고를 쓴다"를 보여 주려면 **회고 글보다 회고가 만들어지는 길**이 작품이다.

```
CC 세션들 ─hook·트랜스크립트→ 브리지 ─→ DB(턴 · 커밋 · 승인 · 디스패치 · 토큰)
                                           │ 기계적 재료 묶음(비밀값 가림)
                                           ▼
                                  서기 초안(문장마다 근거 표시)
                                           │ 근거 확인(기계) → 점검 역할 검토(AI)
                                           ▼
                                  사람 [합치기] — 고친 양을 잰다
                                           │ [게시]
                                           ▼
                                       Notion 포트폴리오
```

**보여 줄 수 있는 것:**
- 근거가 달린 글
- 기계 확인과 AI 검토의 분업
- 사람이 고친 양이 시간이 갈수록 주는 그래프
- 일감마다 쓴 토큰

**조심할 것:** AI 회고는 쉽게 밋밋해진다("소통이 중요했다"). 읽는 사람이 보고 싶은 것은 **판단**이다.
- 그래서 재료 묶음은 사람이 정정한 곳 · 거절한 승인 · 뒤집힌 결정 · 실수를 앞에 둔다

  - 영어 진행 글을 hook으로 잡은 일
  - '푸른 고래' 오해

## 11. 받는 함 [＋ 할 일] (11-09) [log:todo_inbox_20261109.md] [log:coder_resident_20261109.md]

**세션을 거치지 않고 할 일을 그대로 적고, 서기가 몰아서 README 「나중에 할 일」로 옮긴다.** 11-09 관리자 세션에 온 지시 중 "할 일에 넣어라"가 10건쯤이었고, 이것이 맥락을 쌓아 두 번 인계한 주된 까닭이었다 [log:dispatch_flow_decision_20261109.md].

### 11-1. 적는 곳

- 머리줄 **[＋ 세션] 옆 [＋ 할 일]**(`bridge/static/js/todoinbox.js`). 할 일은 여러 프로젝트에 걸치는 일이 많아 머리줄에 두고, 프로젝트는 지금 보는 탭이 기본(11-09 사용자 결정)
- 창: 프로젝트 · **누구에게(서기 정리 / 코더에게)** · 글 칸(Ctrl+Enter) · [적기](primary) · [닫기]. 결과 띠 "적었습니다 — … #번호", 못 적으면 까닭과 "글은 칸에 그대로 있습니다"
- 창 아래 접힌 "받은 할 일 — 최근 N개 · 새로 N": 상태 · 시각 · 첫 글 줄, 펼치면 원문, 새로면 [버리기]
- 표 `todo_inbox`(`migrations/0027_todo_inbox.sql` · `0028_todo_inbox_assignee.sql`): id · project · body(8,000자까지) · assignee(`scribe` 기본 · `coder`) · created_at · taken_by(가져간 세션) · taken_at · dropped_at
- 왜 새 표인가: `foreman_note`는 글 300자 · 프로젝트당 2k 토큰 상한이라 받은 글(대개 600자 넘음)이 잘린다. README 표에 브리지가 바로 커밋하면 여러 세션이 README를 같이 고칠 때 충돌한다

### 11-2. 상태는 칸이 아니라 계산한다

`bridge/scribe_room.py` `_INBOX_STATE` — 합치기 코드를 건드리지 않고 `session_action` · `character_session`에서 센다.

| 상태 | 언제 | 화면(서기 몫) | 화면(코더 몫) |
|---|---|---|---|
| `dropped` | 사람이 [버리기] | 버림 | 버림 |
| `new` | 아무도 안 가져감, 또는 가져간 세션이 버려짐(`wt-discard`) | 새로 | 새로 |
| `taking` | 가져간 세션이 아직 열림 | 서기가 정리 중 | 코더가 하는 중 |
| `moved` | 가져간 세션이 합쳐짐(`wt-merge`). 코더 몫은 원본 폴더 세션이 끝나도 | 옮김 | 끝남 |

### 11-3. 누가 가져가나

- **서기 몫** — 「나중에 할 일 정리」(`later`)가 띄울 때 가져간다. 재료 파일 맨 앞에 "받은 할 일 #번호"를 **모두** 넣는다("그때뿐"으로 거르지 않는다), README 근거 칸에 `받은 할 일 #번호`. 미룬 말도 받은 할 일도 없으면 띄우지 않는다. 서기 몫만 가져간다
- **코더 몫** — 「코더」 패널의 [계획으로] → 감독실 계획 → [이대로 시작]이 `inbox_id`를 실어 보내고(`POST /api/foreman/start`), 뜬 세션이 가져간다(`taken_by`). 이미 다른 세션이 가져갔으면 시작은 막지 않고 적지만 않는다 → `docs/10_office_design.md` 「코더 상주 · 임시 일꾼 · 맡길 일」
- 11-10 첫 실제 정리: 받은 할 일 #2 ~ #11이 서기 237이 합쳐진 뒤 「옮김」 — 적기 → 가져감 → 합치면 옮김이 끝까지 돌았다 [log:merge_237_242_20261110.md]

### 11-4. 조용히 쌓이지 않게

- 서기 할 일(머리 위 "할 일 N")에 "받은 할 일 N개", 새로인 채 **3일**(`INBOX_STALE_DAYS`)이 넘으면 "— 가장 오래된 것 N일째". 텔레그램은 보내지 않는다
- **"정리할까요?"** — 서기 몫 새로가 `new_min`개 이상이거나 가장 오래된 것이 `oldest_days`일이면 서기 머리 위 말풍선(`config/scribe.toml [nudge]`, 기본 3 · 3, 없으면 코드 기본값). 누르면 서기 창이 「나중에 할 일 정리」 줄을 밝히고 그 [시키기]를 primary로 연다. **자동은 제안까지만 — 세션은 사람이 [시키기]를 눌러야 뜬다**(2절의 "할 일은 세고, 실행은 사람이 누른다"와 같다). 값을 바꾸면 브리지를 다시 띄운다

### 11-5. API

- `POST /api/scribe/inbox` `{project, body, assignee}` → 201 `{id}`. 빈 글 · 8,000자 넘음 · 모르는 받는 사람 · 모르는 프로젝트는 409 `{refused}`
- `GET /api/scribe/inbox?project=&limit=` — 최근 것부터(버린 것도), 줄마다 `label`(받는 사람에 맞는 상태 이름) · `to`
- `POST /api/scribe/inbox/{id}/drop`

### 11-6. 남은 것

- 텔레그램으로 할 일 받기(밖에서 적기)는 하지 않았다 — 필요하면 같은 API로

## 12. 물어보기 (11-10) [log:scribe_ask_20261110.md]
