## 3. 돌리기 · 확인

- 브리지는 systemd 사용자 유닛 `foreman-bridge`가 돌린다(11-06, `deploy/systemd/foreman-bridge.service`, linger 켬 — 부팅 때 자동 기동). 상태 · 로그: `systemctl --user status foreman-bridge`, `journalctl --user -u foreman-bridge -n 100`. 다시 띄우기(승인 대기 — `/api/dashboard`의 approvals pending — 가 없는지 본 뒤): `systemctl --user restart foreman-bridge`(10초 남짓 끊김)
  - CC 세션 셸에서는 `systemctl --user`가 `Process org.freedesktop.systemd1 exited with status 1`로 실패한다(세션 환경의 DBUS가 VNC 쪽 버스를 가리키고 `XDG_RUNTIME_DIR`가 비어 있다, 11-08 — 11-09에도 세 세션이 같은 일을 겪었다, 샌드박스 밖에서도). 앞에 `XDG_RUNTIME_DIR=/run/user/1000 DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus`를 붙인다(`journalctl --user`도 같다) [log:screen_argocd_read_20261109.md] [log:handoff_replace_main_20261109.md]
    ```
    XDG_RUNTIME_DIR=/run/user/1000 DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus systemctl --user restart foreman-bridge
    ```
  - **systemd가 다시 띄우기를 포기하면 브리지 밖에서 알린다**(11-15 `cd14ed6`): 유닛 `[Unit]`의 `OnFailure=foreman-bridge-alert.service`(`deploy/systemd/foreman-bridge-alert.service`, `Type=oneshot`)가 `scripts/foreman-bridge-alert.sh`를 부른다. 스크립트는 curl과 `.env.telegram`만 쓰고 브리지 코드, `.venv`, `notify.toml`을 읽지 않는다(접두어 `[FOREMAN]`은 스크립트에 박혀 있어 notify.toml을 바꾸면 손으로 맞춘다). `OnFailure`는 자동 재시작 전 실패마다도 불리므로(systemd 259 실측) 유닛이 정말 `failed`일 때만 보낸다. 글에는 결과, 다시 띄운 횟수, journal 마지막 줄의 예외 클래스 이름만 싣는다. 못 잡는 것: 포기하지 않는 느린 반복, 살아 있지만 답하지 않는 멈춤(바깥 감시 타이머 몫, 아직 없음) [log:foreman-6_bridge_alert_20261115.md]
    - 설치(11-16 확인: 깔려 있다, `systemctl --user show foreman-bridge -p OnFailure`가 `foreman-bridge-alert.service`): `systemctl --user link <저장소>/deploy/systemd/foreman-bridge-alert.service` 뒤 `daemon-reload`(차례를 바꾸면 없는 유닛을 가리킨다). 브리지를 다시 띄울 필요는 없다
  - **훅이 판정 없이 통과하면 `.run/hook_miss.log`에 한 줄 남는다**(11-15 `cd14ed6`, 스크립트 쪽은 `58f9f03`에서 다시 넣음). 브리지가 판정을 내지 못하면 PreToolUse는 막지 않고 통과한다(설계 그대로, `docs/11_worktree.md` 「7.」). 통과는 그대로 두고 사실만 적는다. 정상 판정 길(204 포함)에서는 쓰지 않는다
    - 줄 꼴: `<시각> <출처> <갈래> <까닭> session=<id> tool=<도구>`. 출처는 `script-pre`, `script-permission`(`scripts/foreman-decide.sh`) 또는 `bridge`(`bridge/hookmiss.py` `record`). 명령 글과 입력 값은 쓰지 않는다
    - 갈래 이름은 코드가 정한다(`bridge/hookmiss.py`, `scripts/foreman-decide.sh`) [log:foreman-6_bridge_alert_20261115.md]
    - 1MB를 넘으면 `.1`로 한 벌만 돌린다(약 2MB가 끝). 시험은 `FOREMAN_HOOK_MISS_LOG`로 자리를 바꾼다(위 「2.」 시험 줄)
    - 이 파일을 읽어 알리거나 화면에 올리는 것은 아직 없다. 브리지를 다시 띄우는 틈에 남는 줄은 정상이다
  - **브리지를 다시 띄워야 하는 것은 파이썬(브리지) 변경뿐**이다. js · css · html은 재시작 없이 바로 나간다(`cache-control: no-cache`). 열린 탭은 화면 코드 지문(`bridge/uiver.py` — static 아래 파일 이름 · 크기 · 수정 시각, WS `hello` · `/api/dashboard`의 `ui`)이 바뀌면 맨 위 노란 띠 "화면 코드가 바뀌었습니다. 새로 고쳐야 바뀐 기능이 보입니다."와 [새로 고침] 버튼이 뜬다(저절로 고치지 않는다 — 입력 칸 글이 날아간다) [log:pixel_bigger_question_card_20261109.md] [log:screen_mismatch_waits_20261109.md]
- 브리지 주소는 `127.0.0.1:8000`이다(API 시험 때)
- pytest 끝 요약의 「화면 말 시험: 서기 몫 N줄 남음 …」은 화면 말 시험(`tests/test_screen_words.py`)이 남긴 수다. 서기 몫이 0이 아니면 서기가 이 문서와 `docs/style_guide.md`를 맞추고 `tests/data/screen_words.toml`의 `[[scribe]]` 줄을 지운다. 상세는 `docs/11_worktree.md` 「8.」. 11-17부터 서기 몫은 이름을 바꾼 코더가 고칠 수 없었던 줄만이다(코더가 먼저 고친다, 사용자 지시 21)
- 코드가 바뀌어 밀린 문서는 거꾸로 찾기로 본다: `.venv/bin/python tools/docrefs.py --range <A>..<B> --unfixed`(읽기만, `docs/11_worktree.md` 「9.」). 합치기 카드에도 「걸리는 문서 N, 안 고침 M」으로 보인다
- **시험 DB는 세션마다 따로다**(11-11, 합친 뒤부터 [log:test_db_per_session_20261111.md]). 그래서 "다른 pytest가 도는지 보고 기다린다 / 혼자 돌린다"는 이제 필요 없다(pgrep 확인도 하지 않는다)
  - 이름: `foreman_test_<자리>_<pid>` — `<자리>`는 `.worktrees/<이름>`이면 그 이름(소문자 · 24자까지), 원본 폴더면 `main`. pid는 pytest 프로세스 것이라 같은 worktree에서 둘을 같이 돌려도 겹치지 않는다. 마이그레이션도 그 DB에 이 폴더의 `migrations/`를 올려서 세션마다 갈린다
  - 시작 머리글에 `시험 DB: <이름>`이 찍힌다. 끝나면 지우고(Ctrl+C도 같다), 죽어서(`kill -9` · 세션 종료) 남은 것은 **다음 pytest가 뜰 때** 이름 끝 pid가 죽은 것만 치운다(자리 이름은 보지 않는다 — 다른 세션의 살아 있는 시험은 안 지운다)
