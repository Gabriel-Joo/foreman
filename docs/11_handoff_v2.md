## 2. 인계 2판 — 세 단계

### ① 문서로 옮기기 (넘기기 전)

브리지가 세션에 요청을 넣으면, 세션은 이 대화에서 정했지만 아직 문서에 없는 것을 뽑는다. 대상은 결정 · 금지 · 기준 · 선호 · 미완이고, 항목마다 아래를 낸다.

| 칸 | 예 |
|---|---|
| 무엇 | "마이그레이션은 RENAME 대신 추가 + 복사, DROP은 안정된 뒤 따로" |
| 원문 | 사용자 말 그대로(턴 번호) |
| 어디로 | `CLAUDE.md` 금지, `docs/07_database.md` 3절, 메모리(사람 선호), 버림(일회성), 포스트잇(끝나지 않은 할 일, `postit`) |
| 왜 거기 | CLAUDE.md는 꼭 지킬 것만 짧게(사용자 기준), 상세는 docs |

- 사람은 패널에서 목록을 보고 고친다. 목적지를 바꾸거나 빼거나 승인한다.
- 승인한 것만 세션이 그 파일에 쓰고 커밋한다(`인계 전 결정 기록: …`).
- 종류 미완(할 일)은 README가 아니라 포스트잇으로 간다(11-15, dest `postit`). 세션이 dest를 비우거나 `README.md`로 내도 브리지가 `postit`으로 바꾼다. 규칙과 결정은 지금처럼 docs, style_guide, CLAUDE.md로 간다
- dest `postit`은 2/2에서 세션에 보내지 않는다. 브리지가 포스트잇에 넣고(출처 promote, 근거 `pr:<promotion id>:<항목 id>`, 같은 근거는 두 번 넣지 않는다) 결과 `postit`에 id를 남긴다. 승인한 것이 모두 포스트잇이면 쓰기 요청 없이 바로 끝난다(`bridge/promote.py` `_postit`)
- worktree 세션이면 그 브랜치에 쓴다.
- 압축 손실 점검 결과가 있으면 그 "사라짐" 목록도 같이 넣는다. 세션 기억에서 이미 빠진 것을 원문에서 되살리는 길이다.
- **서기가 이 단계를 맡을 수도 있다**(12단계 `loss` · `trim` 일감). 처음에는 세션 자신이 하고, 서기가 생기면 넘긴다.

### ② 짧은 인계 + 읽을 곳

요약은 2,500자 안으로 줄이고 **문서에 없는 것만** 쓴다.

```
<<<FOREMAN-HANDOFF r=…>>>
## 지금 상태
(어디까지 왔나 — 커밋 해시 · 브랜치 · 돌고 있는 것. 5~8줄)
## 다음 할 일
(순서대로 3~5개)
## 걸려 있는 것
(승인 대기 · 서브에이전트 · 타이머 · 커밋 안 한 변경 · 사람이 하기로 한 것)
## 문서와 다른 지금
(문서에는 X라고 적혀 있지만 지금은 Y — 문서를 아직 못 고친 것만. 없으면 "없음")
## 읽을 곳
- CLAUDE.md 「작업 규칙」 — 매번(자동으로 읽히지만 금지 항목을 다시 확인)
- docs/01a_catalog_sources.md 「스펙 출처 우선순위」 — 다음 할 일 2에 필요
- log/runshoes_compaction_loss_20261105.md 「지금 작업에 바로 걸리는 것」
<<<END r=…>>>
```

**브리지가 넣기 전에 기계로 확인한다.**
- 읽을 곳의 파일이 있는가, 절 제목이 실제로 있는가
  - **(11-15 사용자) 읽을 곳은 줄 번호가 아니라 절 제목으로 가리킨다** — 문서가 조금만 짧아져도 줄 번호는 깨진다(관리자 410 인계의 `docs/11_worktree.md:224-260`이 239줄 문서에서 막혔다). 인계 요청 글(`handoff.py REQUEST_PROMPT_V2`)은 「`경로` 「절 이름」」과 「`경로`」 두 꼴만 권한다. 확인(`bridge/pointers.py`)은 옛 인계 · 사람이 쓴 것을 위해 줄 범위(`:a-b`)를 계속 받되, 틀리면 거부 글에 그 자리의 절 제목을 붙인다: 「줄 범위가 맞지 않습니다(파일은 239줄). 줄 번호 대신 절 제목으로 가리켜 주세요(예: `docs/11_worktree.md` 「8. 화면 말을 바꿀 때」)」. 제목은 시작 줄 위로 가장 가까운 `#` 제목이다(파일보다 길면 끝 줄 기준, 코드 울타리 안은 뺌, `section_hint`). 긴 제목은 첫 덧말(` — ` · ` (` · ` [`) 앞까지만 쓴다. 절 확인이 부분 맞춤이라 앞부분으로도 통한다
- 각 문서의 마지막 커밋 시각을 옆에 붙인다. 그 일과 관련된 코드보다 오래됐으면 "문서가 오래됐을 수 있음"으로 표시한다
- 틀린 곳은 패널에 띄우고, 고치기 전에는 넣지 않는다
- **어느 폴더를 기준으로 보나(11-09)**: 새 세션은 늘 기준 브랜치(main) 내용으로 시작한다(원본 폴더에서 뜨거나, 새 worktree도 base에서 가른다). 그래서 **원본 폴더**를 기준으로 본다 — 요약을 쓴 세션의 폴더가 아니다(쓴 worktree가 뒤처지면 main에 있는 절을 "없다"고 막았다, 런슈즈 인계 #14). 원본에 없고 쓴 worktree에만 있으면 "원본 폴더에는 아직 없고 요약을 쓴 worktree에만 있습니다(합친 뒤 넣습니다)"로 막는다. "이 문서 뒤로 커밋 N개"도 원본 폴더 기준. 근거는 `log/handoff_pointer_basis_20261109.md`

### ③ 새 세션이 실제로 읽게

넣는 글:

> 먼저 「읽을 곳」을 모두 Read로 읽어라. 읽은 뒤 (1) 각 문서에서 이 일에 걸리는 규칙 · 결정을 2줄씩 (2) 「문서와 다른 지금」을 어떻게 다룰지를 말하고, 사용자의 확인을 기다려라.

- **브리지가 확인한다.** 새 세션의 첫 턴 도구 이벤트(`Read` · 대상 경로)를 읽을 곳 목록과 맞댄다.
- 패널에 "읽을 곳 5/6 읽음, 안 읽음:docs/07"을 보이고, [안 읽은 곳 다시 보내기] 버튼을 둔다.
  - (11-09) 받은 세션은 **그 세션의 폴더**(실제로 읽는 곳)를 기준으로 본다. 거기 없는데 원본 폴더에는 있으면 "이 작업방이 main보다 커밋 N개 뒤처졌습니다(main에는 있습니다). fast-forward하면 읽을 수 있습니다"
  - 확인에 실패한 곳(파일 · 절 · 줄이 없음)은 Read를 했어도 **읽음에서 뺀다** — "4/6 읽음 · 확인 실패 2"와 ✗ 줄. [안 읽은 곳 다시 보내기]는 안 읽은 곳에만
- 1판처럼 요약 본문을 통째로 넣지 않으므로 새 세션의 시작 맥락이 작다. 문서가 최신이면 맥락도 최신이다.

### 틀린 문서의 위험

문서가 지금과 다르면 틀린 맥락이 들어간다. 세 겹으로 막는다.
1. **「문서와 다른 지금」 칸.** 인계를 쓰는 세션이 아는 차이를 적는다. 기억에서 나오는 것은 이 칸뿐이다.
2. **오래된 문서 표시.** 위 ②의 기계 확인이다.
3. **서기의 `sync` 일감.** 문서를 코드 · 커밋에 맞춰 둔다. 그래서 이 방식에서는 서기가 핵심이 된다.
4. **인계 검증(11-06, `bridge/handoff_state.py`).** 인계 자체가 낡는 것도 막는다. 요약을 만들 때 git(저장소 · worktree · 브랜치 · HEAD · 기준 브랜치 HEAD)과 스키마 잠금을 `summary.state`에 적고, 넣을 때(미리보기 포함) 지금과 비교한다. 다르면 넣는 글 맨 앞에 「인계 뒤 바뀐 것」(worktree가 없어짐 · 합쳐짐 · 기준 브랜치의 새 커밋 · 읽을 곳 중 바뀐 파일 · 잠금 주인)을 붙이고 받은 세션에 "지금 상태를 직접 보고 다시 판단하라"고 한다. 붙인 줄은 `summary.drift`에 남아 받은 세션 패널에도 보인다. 상태 기록이 없는 옛 인계는 "직접 확인하라" 한 줄이 붙는다. 근거: 인계 r=690cec를 받은 세션이 이미 합쳐진 c · 없어진 worktree · 바뀐 잠금을 "지금 상태"로 받았다

## 3. 압축 알림

### 언제 — 실제 기록으로 정한 선

| 후보 | 기록 | 판단 |
|---|---|---|
| **압축 횟수** | 손실의 76%가 압축 두 번 안 | **쓴다.** 2번째 압축 직후 "넘어갈 때", 4번째부터 "늦었음" |
| 트랜스크립트 크기 | 런슈즈 735MB/19번, 펫퍼민트 393MB/12번, 포먼 98MB/7번 | **안 쓴다.** 크기는 거의 도구 출력이라 횟수와 함께 늘 뿐 더 알려 주는 게 없다 |
| 압축 간격 | 압축 사이 사람 턴 2~36으로 들쭉날쭉. 짧은 간격은 큰 도구 출력 때문이고 줄어드는 추세는 없다 | **보조로만.** 압축 사이 사람 턴이 3 이하로 두 번 이어지면 "맥락이 금방 찬다"고 덧붙인다 |
| 압축 직후 | 압축 직후는 맥락이 1~2만 토큰으로 가볍다 | **알리는 시점으로 쓴다.** 인계 요청을 넣어도 비용이 작다 |

- 횟수는 **세션 시작(또는 마지막 인계를 받은 때)부터** 센다
- 기준 2 · 4는 `config/notify.toml`에 둔다(바꿀 수 있다)
- 압축이 없어도 맥락이 300k · 500k를 넘으면 알린다(11-08). 쉬어서 캐시가 식은 세션은 요약이 오히려 비싸다 — `docs/15_usage.md` 6-1절

### 쌓인 대화 비율 · 작업 전환 권유 (11-09)

브리지 쪽 판정만 적는다. 패널 표시(머리줄 "쌓인 대화 N%", 🧠 띠의 %, 🔀 띠)는 `log/foreman-2_screen_ctx_switch_overlap_20261109.md`, 이름 나누기는 `docs/style_guide.md` 「4-1. 화면 글」. [log:foreman_context_pct_20261109.md]

- **창 크기 `config/models.toml [windows]`** — 모델 id별(11-14부터, 없으면 family로도 찾는다). claude-opus-5-5 1,000,000(실측 — 응답 하나의 맥락이 971,510까지 갔다), claude-haiku-5-5 200,000(**추정** — 지금까지 본 최대 114k). claude-sonnet-5-5는 200,000으로 추정했다가 본 대화 맥락 223,147(11-13)이 보여 11-14에 뺐다(모름), claude-opus-5 · claude-fable-5-2도 모름 [log:foreman-3_model_menu_20261114.md]. DB `message.model`에 `[1m]` 같은 접미사가 없어 모델 id로는 창을 알 수 없어 설정으로 둔다(`model_choice.window_of`). 목록에 없는 모델은 %를 보이지 않고 토큰(k)만
- **비율 = 마지막 응답 맥락(입력 + 캐시 읽기 + 캐시 쓰기) ÷ 창**(`compactwatch.context_status` → `window` · `pct` · `window_over`, `/api/dashboard`의 세션 `context`에 그대로)
- **문턱 `config/notify.toml [compact]`** — `context_at = [300000, 500000]`(토큰) · `context_pct = [50, 75]`(비율). 둘 중 **먼저 닿는 쪽**이 단계(첫 값 "넘어갈 때", 끝 값 "늦었음")를 정한다
  - 토큰 문턱은 비용(응답마다 맥락 전체를 다시 읽는다)에서, 비율 문턱은 창이 작은 모델에서 토큰 문턱이 영영 닿지 않는 틈(200k 창이면 300k는 도달 불가)을 메우려고. 75%는 자동 요약(창 80~90%) 직전 마지막 경고, 50%는 요약 전에 손실 없이 옮기기 좋은 때
  - 1M 창(Opus)은 토큰 문턱이 먼저 닿아(300k → 30%, 500k → 50%) 동작이 그대로다. 실제 세션 80개를 새 기준으로 돌려 달라진 것은 둘 — 197 Haiku 114k(57%) · 228 Sonnet 141k(71%)가 없음 → 넘어갈 때
  - 텔레그램은 세션 · 단계마다 한 번(kind `context`, rule `ctx:<넘은 토큰 문턱>` 또는 `pct:<비율 문턱>` — 단계를 만든 쪽)
- **창 초과 `over:` 알림** — 맥락이 설정한 창보다 크면 `[windows]` 값이 틀렸다는 신호다. 세션 · 창마다 텔레그램 한 번(kind `context`, rule `over:<창>`) + 경고 로그, %는 100%로 막는다: "… 쌓인 대화가 Nk로, 설정한 <모델> 창 Nk보다 큽니다. 창 크기 값이 틀렸습니다 — config/models.toml [windows]를 고쳐야 쌓인 대화 %가 맞습니다." 11-09 다시 돌림에서 0건
- **작업 전환 권유(`bridge/switchwatch.py`)** — 사람 턴마다 본다(`compactwatch.check_switch`). 세 가지가 겹칠 때만(하나씩은 약하다):
  1. 가장 최근 사람 요청 **앞머리 160자**에 전환 말("다음 일" · "다른 건" · "이번엔" · "넘어가" · "별개로" · "moving on" 등)
  2. 그 요청 직전 **30분 안 커밋** 또는 직전 턴 끝 뒤 **20분 넘는 쉼**
  3. 쌓인 대화 ≥ `switch_min_pct`(40%). 창을 모르는 모델은 권하지 않는다
  - 텔레그램 한 번(kind `switch`, rule `switch:<턴 id>`): "[프로젝트] 세션 「…」 다른 일로 넘어가시는 것 같습니다 — 방금 커밋했고 지금까지 쌓인 대화가 N%입니다. 새 일은 새 세션에서 시작하면 응답이 빠르고 쌉니다. 패널에서 [새 세션으로 옮기기]를 누르세요. (옮기기 전에 대화에서만 정한 결정은 문서로 옮겨 둡니다)". 숨긴 세션은 보내지 않는다. 막지 않는다
  - **패널 띠로도 뜬다** — `/api/dashboard` 세션의 `switch: {turn_id, phrase, committed, idle, pct}`(없으면 null). 판정은 텔레그램과 같은 함수(`switchwatch.latest_signal` · `should_suggest`)를 쌓인 대화 ≥ `switch_min_pct`인 세션만 다시 부른다. [나중에]는 그 사람 턴 동안만 숨긴다 [log:foreman-2_screen_ctx_switch_overlap_20261109.md] [log:merge_foreman2_check_20261109.md]
  - clear가 아니라 새 세션으로 옮기기를 권하는 까닭 — 대화에서만 정한 결정은 문서로 옮긴 뒤 넘겨야 한다(1장)
- 확인 안 된 것: Sonnet · Haiku 창 크기(추정 200k). 큰 기록이 보이면 `over:` 알림이 온다
  - (11-14 바뀜 → Sonnet은 223k 맥락이 보여 `[windows]`에서 뺐다(모름, %를 보이지 않는다). 추정으로 남은 것은 Haiku 200k. 이 절 첫 줄)
